### Libraries and packages
- A ==library== is reusable code your script imports instead of writing itself
  - `Jinja2` renders templates, `PyYAML` parses YAML, `netmiko` drives SSH to switches, `requests` calls REST APIs
- A ==package== is the distributable bundle that delivers a library
  - Code plus metadata: name, version, and the packages *it* needs
  - Python packages come from PyPI as wheels; Node packages from npm; Ansible collections from Galaxy
  - Operating systems have packages too: `apt` and `dnf` install `.deb` and `.rpm` files
- A package manager downloads, installs, upgrades, and removes packages: `pip`, `npm`, `apt`, `ansible-galaxy`
- ==Dependencies== are the packages your code needs
  - Direct: the ones you asked for
  - ==Transitive==: the ones your dependencies need (Jinja2 pulls in MarkupSafe)
- ==Dependency management== keeps that set declared, versioned, and reproducible
  - "Works on my laptop" usually means a different version of something installed somewhere else

### requirements.txt
- The plain-text list of packages a Python project needs, one per line
  - Install everything with `pip install -r requirements.txt`
- ==Pinning== fixes the exact version so every install is identical

| Line | Installs |
|---|---|
| `Jinja2==3.1.6` | exactly 3.1.6 (pinned) |
| `Jinja2>=3.1,<4` | newest 3.x at or above 3.1 |
| `Jinja2~=3.1.2` | 3.1.2 or newer, still 3.1.x |
| `Jinja2` | whatever is newest today |

- Pin for automation that runs unattended (pipelines, scheduled jobs)
  - An unpinned dependency can change between Monday's run and Tuesday's
  - Update pins on purpose, test, then commit the new file
- `pip freeze` lists every installed package, transitive ones included, in pinned form
- `--require-hashes` adds a checksum per package so a tampered download fails

```text label="requirements.txt"
# runtime libraries for render.py
Jinja2==3.1.6
PyYAML==6.0.3
```

- `render.py` turns the `switch.yaml` from Data Types into switch config lines

```python label="render.py"
import sys
import yaml
from jinja2 import Template

TEMPLATE = Template(
    "hostname {{ hostname }}\n"
    "{% for v in vlans %}vlan {{ v }}\n{% endfor %}"
)
with open(sys.argv[1]) as f:
    data = yaml.safe_load(f)
print(TEMPLATE.render(**data), end="")
```

### Virtual environments
- A ==virtual environment== (venv) is a private copy of Python with its own `site-packages` folder
  - One per project; projects stop fighting over versions
  - Installs need no root and never touch the system Python that OS tools rely on
- Debian 12+ and Ubuntu 23.04+ mark the system Python as externally managed
  - A bare `pip install` there fails with `error: externally-managed-environment`
- Keep `.venv/` out of Git (`.gitignore`); commit `requirements.txt` instead
  - Anyone can rebuild the same environment from the file

```console label="Terminal"
$ python3 -m venv .venv
$ . .venv/bin/activate
$ pip install -q -r requirements.txt
$ pip freeze
Jinja2==3.1.6
MarkupSafe==3.0.4
PyYAML==6.0.3
$ python render.py switch.yaml
hostname core-sw1
vlan 10
vlan 20
vlan 30
```

- `deactivate` returns to the system Python
- MarkupSafe appeared without being asked for: a transitive dependency
  - It is not pinned, so a later install may bring a newer MarkupSafe
  - To pin it too, write `pip freeze > requirements.txt`, or use a lock tool (`pip-tools`, `uv`, Poetry)

### Dependencies in a Dockerfile
- A ==Dockerfile== builds an image that carries the code, the runtime, and every dependency
  - The same image runs on a laptop, in CI, and in production
- Order instructions from least to most frequently changed
  - Each instruction becomes a cached ==layer==; a change rebuilds that layer and everything after it
  - To keep the ==build cache== useful, copy `requirements.txt` and install it before copying the code, so a code edit does not reinstall packages

```dockerfile label="Dockerfile"
FROM python:3.13-slim
WORKDIR /app
COPY requirements.txt .
RUN pip install --no-cache-dir -r requirements.txt
COPY render.py switch.yaml ./
ENTRYPOINT ["python", "render.py"]
CMD ["switch.yaml"]
```

:::figure 1.1-docker-layers.svg | Editing render.py invalidates only the layers from its COPY down. The pip install layer comes from cache.

```console label="Terminal"
$ docker build -q -t cfg-render:1.0 .
sha256:07bb04430c43fe146b60bbd9944bda41...
$ docker run --rm cfg-render:1.0
hostname core-sw1
vlan 10
vlan 20
vlan 30
```

- After editing only `render.py`, a rebuild with `--progress=plain` prints `CACHED` for `WORKDIR`, `COPY requirements.txt`, and `RUN pip install`; only the last `COPY` runs again
  - Changing a pin in `requirements.txt` rebuilds the install layer, as it should
- Pin the base image tag (`python:3.13-slim`), never `latest`
- `--no-cache-dir` keeps pip's download cache out of the image
- OS packages: one `RUN` that chains `apt-get update` and `apt-get install -y --no-install-recommends`, so the package list is never stale

### Other ecosystems
- Same idea everywhere: a ==manifest== names what you need; a ==lock file== records exactly what was installed

:::wide
| Ecosystem | You declare | Exact versions recorded in | Install |
|---|---|---|---|
| Python | `requirements.txt` or `pyproject.toml` | pinned `requirements.txt`, `uv.lock`, `poetry.lock` | `pip install -r requirements.txt` |
| Node.js | `package.json` | `package-lock.json` | `npm ci` |
| Ansible | `collections/requirements.yml` | versions in the same file | `ansible-galaxy install -r` |
| Terraform | `required_providers` block | `.terraform.lock.hcl` | `terraform init` |
| Go | `go.mod` | `go.sum` | `go mod download` |
:::

- Commit lock files to Git so CI installs the same versions you tested
- Scan dependencies for known vulnerabilities: `pip-audit`, `npm audit`, Dependabot

:::exam
- A scenario where a script works on one machine and fails on another after "nothing changed" points to an unpinned dependency or a missing virtual environment. The fix is a pinned `requirements.txt` (or lock file) installed in a venv or container.
- Know the vocabulary: a library is code you import; a package is how it is distributed; a transitive dependency is one your dependency needs.
- In a Dockerfile, copying `requirements.txt` and running `pip install` before copying the code keeps the install layer cached.
:::
