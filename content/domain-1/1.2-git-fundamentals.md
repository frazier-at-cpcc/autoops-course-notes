### Why automation code lives in Git
- Every change is recorded
  - Who made it, when, and the message explaining why
  - Roll back a bad change in seconds instead of rebuilding by hand
- Automation code is production code
  - Scripts, Ansible playbooks, Terraform files, pipeline YAML
  - A typo in a playbook can take down every switch it touches
- Git is a ==distributed version control system==
  - Every clone holds the complete history
  - Work offline, sync with the team later
  - No single copy is the only copy
- The repository is also the trigger
  - Pushing a commit is what starts most CI pipelines (Domain 3)

### Three local areas, one remote
- ==Working tree==
  - The files you see and edit in the project folder
- ==Staging area== (also called the ==index==)
  - The changes you have selected for the next commit
  - Lets you commit one fix while other edits stay uncommitted
- ==Local repository==
  - The `.git` folder: every committed snapshot
- ==Remote repository==
  - A shared copy on a server such as GitHub, GitLab, or a self-hosted Gitea
  - Your commits stay private to your machine until you push them

### git config
- Settings live at three levels
  - `--system`: every user on the machine (`/etc/gitconfig`)
  - `--global`: your user account (`~/.gitconfig`)
  - `--local`: one repository (`.git/config`), the default when no flag is given
  - The most specific level wins: ==local overrides global, global overrides system==
- Set your identity before your first commit
  - Name and email are written into every commit you make

```console label="Terminal"
$ git config --global user.name "Ada Admin"
$ git config --global user.email "ada@example.com"
$ git config --global init.defaultBranch main
$ git config --list --show-origin
file:/home/ada/.gitconfig   user.name=Ada Admin
```

- `--show-origin` prints the file each setting came from
  - The fastest way to find out why a setting is not what you expect
- Settings you will meet later in these notes
  - `core.hooksPath`: a shared folder of hooks
  - `pull.rebase`: rebase instead of merge on pull
  - `versionsort.suffix`: correct ordering of pre-release tags

### git add
- Copies changes from the working tree into the staging area
  - `git add switch.cfg`: one file
  - `git add .`: everything under the current folder
  - `git add -p`: walk through each change and choose
- `git status` shows what is where

```console label="Terminal"
$ git status --short
?? banner.txt
?? switch.cfg
$ git add switch.cfg
$ git status --short
A  switch.cfg
?? banner.txt
```

- `??` is untracked; `A` is staged as a new file; `M` is modified
- ==.gitignore== lists files Git should never stage
  - `.env`, `*.pem`, `.terraform/`, `terraform.tfstate`, build output
  - Keeps secrets and generated files out of history

### git commit
- Saves the staged snapshot to the local repository with a message
- Every commit gets an ID: a ==SHA hash== of its content and metadata
  - 40 hex characters, usually shown as the first 7

```console label="Terminal"
$ git commit -m "feat: add core switch baseline"
[main (root-commit) ffe321e] feat: add core switch baseline
 1 file changed, 1 insertion(+)
$ git log --oneline
1e5e6c6 feat: add login banner
ffe321e feat: add core switch baseline
```

- `git commit -am "msg"` stages tracked files and commits in one step
  - Skips untracked files; new files still need `git add`
- See changes before you commit them
  - `git diff`: working tree versus staging
  - `git diff --staged`: staging versus the last commit

:::exam
- Know which two areas each command moves changes between: `add` is working tree to staging, `commit` is staging to the local repository, `push` is local to remote.
- A commit that has not been pushed does not exist for teammates or for the pipeline. If a scenario says "the pipeline did not run," check whether the change was pushed.
:::
