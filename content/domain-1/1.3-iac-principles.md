### What infrastructure as code means
- ==Infrastructure as code (IaC)==: servers, networks, and services defined in text files that a tool reads and carries out
  - Replaces clicking through a cloud console or typing commands into each switch
  - The files live in Git (objective 1.2): reviewed in pull requests, tagged, rolled back
  - One set of files builds dev, test, and production, so the environments match
- Two jobs, often split between two tools
  - ==Provisioning==: create the infrastructure itself (VMs, VPCs, subnets, DNS records, load balancers)
  - ==Configuration management==: set up what runs inside it (packages, config files, services, users)
- A common pairing: Terraform builds the VMs, Ansible configures them

:::wide
| Tool | Main job | How you write it |
|---|---|---|
| Terraform, OpenTofu | provisioning, any provider | HCL; declarative; tracks a state file |
| AWS CloudFormation, Azure Bicep | provisioning, one cloud | YAML or JSON, Bicep; declarative |
| Pulumi | provisioning | Python, TypeScript, Go, C#; desired-state engine |
| Ansible | configuration (and some provisioning) | YAML playbooks; agentless over SSH or WinRM |
| Puppet, Chef, Salt | configuration | agent on each node; Puppet DSL, Ruby, YAML |
| Packer | machine images | HCL; bakes a VM or cloud image |
:::

### Configuration drift
- ==Configuration drift==: the running system no longer matches its definition
  - A fix typed over SSH during an outage and never written down
  - A setting changed in the console "just to test"
  - Updates applied to some servers and not others
- Drift produces ==snowflake servers==
  - Each one is unique; nobody can rebuild it; everyone is afraid to reboot it
- Drift is the main reason to adopt IaC
  - When the code is the only way changes happen, the code is always the truth
- Detect drift by running the tool in compare mode
  - `terraform plan` prints "Objects have changed outside of Terraform"
  - `terraform plan -refresh-only` reports drift without proposing changes
  - `ansible-playbook --check --diff` shows what a run would change (example in the next topic)
- Schedule it: a nightly pipeline job runs `terraform plan -detailed-exitcode`
  - Exit 0 is no changes, 1 is an error, 2 means a difference exists
- Fix it by applying the code again, or, if the manual change was right, by adding it to the code

### Reusability
- Write a definition once, use it many times with different inputs
  - Forty branch offices, one switch template; a fix reaches every site
- Terraform ==module==: a folder of `.tf` files with input variables and outputs
  - The calling (root) module uses it in a `module` block and passes values
  - Source can be a local path, a Git URL pinned to a tag (`?ref=v1.4.0`), or a registry address with a `version` constraint

```hcl label="modules/switch_config/main.tf"
resource "local_file" "config" {
  filename = "out/${var.hostname}.cfg"
  content = templatefile(
    "${path.module}/switch.tftpl",
    { hostname = var.hostname, vlans = var.vlans }
  )
}
```

```hcl label="main.tf (two calls, one module)"
module "sw1" {
  source   = "./modules/switch_config"
  hostname = "access-sw1"
  vlans    = { "10" = "users", "20" = "voice" }
}

module "sw2" {
  source   = "./modules/switch_config"
  hostname = "access-sw2"
  vlans    = { "10" = "users", "30" = "printers" }
}
```

```console label="Terminal"
$ terraform apply -auto-approve
Apply complete! Resources: 2 added, 0 changed, 0 destroyed.
$ ls out
access-sw1.cfg
access-sw2.cfg
$ cat out/access-sw1.cfg
hostname access-sw1
vlan 10
 name users
vlan 20
 name voice
```

- Ansible ==role==: a standard folder layout that bundles tasks with their defaults, templates, and handlers
  - `ansible-galaxy role init roles/resolver` creates the skeleton
  - A play applies the role and overrides only what differs, such as `resolver_servers` for the Dallas site
  - Share roles through Ansible Galaxy or a private Git repository

| Role folder | Holds |
|---|---|
| `tasks/` | the steps (`main.yml` runs first) |
| `defaults/` | inputs callers may override |
| `vars/` | values callers should not change |
| `templates/` | Jinja2 files for the `template` module |
| `files/` | static files to copy |
| `handlers/` | actions on change, such as a service restart |
| `meta/` | dependencies on other roles |

- Pin the version of every shared module or role; an unpinned upgrade changes every site at once

### Immutability
- ==Mutable infrastructure==: a server is built once, then patched, upgraded, and edited in place for years
- ==Immutable infrastructure==: a running server is never modified
  - To change it, build a new one from a new version and replace the old one
  - Nothing is edited after deploy, so there is nothing to drift

:::figure wide 1.3-mutable-immutable.svg | A mutable server collects changes nobody recorded. An immutable server is thrown away and replaced by one built from the next versioned image.

- How teams make servers immutable
  - ==Golden image==: Packer bakes the OS, agents, and app into a VM template or cloud image, versioned like code
  - Containers: each release is a new image tag; a running container is replaced, not patched
  - Terraform replaces a resource when an argument cannot change in place:

```console label="Terminal"
$ terraform plan
  # module.sw2.local_file.config must be replaced
-/+ resource "local_file" "config" {
      ~ content              = <<-EOT # forces replacement
Plan: 1 to add, 0 to change, 1 to destroy.
```

- `-/+` means destroy, then create the replacement
  - With `lifecycle { create_before_destroy = true }` the symbol is `+/-`: the new one comes up first
  - `terraform apply -replace=<address>` forces a replacement on purpose
- Pros: identical servers; rollback is redeploying the previous image
- Costs: build and deploy must be automated; data and logs must live off the server
- Shorthand: ==pets versus cattle==. Pets are nursed back to health; cattle are replaced.

:::exam
- "A server was changed by hand and no longer matches the template" is configuration drift. The fix is to reapply the code, or to codify the change, not to document it in a wiki.
- "Rebuild from a new image instead of patching the running server" is immutability. "Use the same definition for 40 sites with different values" is reusability: modules in Terraform, roles in Ansible.
- Copying a whole playbook or `.tf` folder per site is the distractor for reusability: every copy must then be fixed separately.
:::
