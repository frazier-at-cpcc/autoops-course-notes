### Branches
- A ==branch== is a movable pointer to a commit
  - Creating one is instant and costs almost nothing
  - Each branch is a separate line of work
- `main` is the default branch
  - Treat it as always deployable
  - Most teams protect it: no direct pushes, changes arrive by review
- The everyday commands
  - `git switch -c feature/x`: create a branch and move to it
  - `git switch main`: go back
  - `git merge feature/x`: bring that work into the current branch
  - `git branch -d feature/x`: delete it once merged
- A ==branching strategy== is the team's agreement on which branches exist, what goes on each, and how work moves between them

:::figure wide branching.svg | Feature branches carry new work into main. Release branches carry a finished version out of main and accept only fixes.

### Feature branching
- One branch per feature, bug, or ticket
  - Created from `main`, merged back into `main`
- Work arrives through a ==pull request== (GitLab calls it a ==merge request==)
  - Teammates review the change
  - The CI pipeline runs lint and tests on the branch before merge
  - Branch protection can require both to pass
- Keeps unfinished work out of `main`
  - Abandon an experiment by deleting the branch
- Keep branches short-lived
  - The longer a branch lives, the further it drifts and the worse the merge conflicts
- ==Trunk-based development== is feature branching taken to its limit
  - Branches last hours or a day; everyone merges to `main` constantly
  - Unfinished features hide behind ==feature flags==

```console label="Terminal"
$ git switch -c feature/NET-142-ntp-servers
$ git commit -am "feat(ntp): add NTP servers"
$ git push -u origin feature/NET-142-ntp-servers
```

### Release branching
- Cut a ==release branch== from `main` when a version is ready to stabilize
  - `release/2.1` or `release/v2.1`
- Only fixes go on the release branch
  - New features keep landing on `main` for the next version
- Tag each release from the branch
  - `v2.1.0`, then `v2.1.1` for the first fix
- Every fix is carried back to `main`
  - Merge the release branch, or `git cherry-pick -x <commit>`
  - Otherwise the bug comes back in 2.2
- Lets you support several versions in production at once
  - Customers on 2.1 get patches while 3.0 is being built
- ==GitFlow== is a heavier model built on the same idea
  - Long-lived `main` and `develop` branches plus feature, release, and hotfix branches

:::wide
| Strategy | Branches live for | Best fit | Watch out for |
|---|---|---|---|
| Feature branching | days | most teams; review before merge | branches that drift for weeks |
| Trunk-based | hours | mature CI, frequent deploys | needs feature flags and fast tests |
| Release branching | a version's support life | several versions in production | fixes not carried back to main |
| GitFlow | develop and main forever | scheduled releases | ceremony and merge overhead |
:::

### Branch naming conventions
- Prefix by purpose
  - `feature/`, `fix/` or `bugfix/`, `hotfix/`, `release/`, `chore/`, `docs/`
- Include the ticket ID so the work links back to the tracker
  - `feature/NET-142-ntp-servers`
- Lowercase words joined by hyphens; no spaces
- Consistent names let automation act on patterns
  - Run the deploy job only on `release/*`
  - Apply branch protection rules to `main` and `release/*`
  - `git branch --list 'release/*'` finds every release line

:::exam
- "Maintain version 1 for existing customers while building version 2" points to release branching.
- "Isolate a new feature until it is reviewed and tested" points to feature branching with a pull request.
- A naming convention exists so tools and people can filter branches by pattern.
:::
