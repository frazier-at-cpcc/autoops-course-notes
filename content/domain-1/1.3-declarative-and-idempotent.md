### Imperative: say how
- ==Imperative== (also called ==procedural==) code lists the steps to carry out, in order
  - Bash, PowerShell, Python, a runbook of CLI commands
  - Each step runs every time, whether or not its work is already done
- Full control, but you own every problem: checking current state, ordering, error handling

```bash label="add-dns.sh"
#!/usr/bin/env bash
# Imperative: steps, run in order, every time
set -euo pipefail
mkdir -p etc
echo "nameserver 10.0.0.53" >> etc/resolv.conf
```

### Declarative: say what
- ==Declarative== code describes the end state; the tool works out the steps
  - Terraform HCL, CloudFormation, Kubernetes manifests, Ansible modules
- The tool compares the ==desired state== (your code) with the ==actual state== (what is running) and changes only the difference
  - Terraform orders the work itself, from the references between resources
- Ansible is a hybrid: each module is declarative (`state: present`, `content:`), but tasks still run top to bottom
- Declarative vs. imperative comes down to what versus how

| | Imperative | Declarative |
|---|---|---|
| You write | the steps | the end state |
| Order | as written | chosen by the tool |
| Run twice | repeats every step | nothing to do |
| Hand edit | not noticed | detected, reverted |

```yaml label="site.yml"
- name: Baseline resolver config
  hosts: localhost
  connection: local
  gather_facts: false
  vars:
    etc: "{{ playbook_dir }}/etc"
  tasks:
    - name: Config directory exists
      ansible.builtin.file:
        path: "{{ etc }}"
        state: directory
        mode: "0755"

    - name: Resolver points at internal DNS
      ansible.builtin.copy:
        dest: "{{ etc }}/resolv.conf"
        content: "nameserver 10.0.0.53\n"
        mode: "0644"
```

### Idempotency
- ==Idempotent==: running an operation once or ten times leaves the system in the same state
  - The second run finds nothing to do and reports no changes
- Why automation depends on it
  - Pipelines rerun jobs; a half-finished run can be retried safely
  - A scheduled run doubles as drift correction
- The imperative script is ==not idempotent==

```console label="Terminal"
$ ./add-dns.sh; ./add-dns.sh
$ cat etc/resolv.conf
nameserver 10.0.0.53
nameserver 10.0.0.53
```

- The playbook is: run 1 ends `ok=2 changed=2`, run 2 only checks
  - `changed`: the task had to act; `ok`: already correct

```console label="ansible-playbook site.yml (second run)"
$ ansible-playbook site.yml
TASK [Config directory exists] ****************
ok: [localhost]

TASK [Resolver points at internal DNS] ********
ok: [localhost]

PLAY RECAP ************************************
localhost                  : ok=2    changed=0
```

- Terraform's second `apply` of the module from the previous topic

```console label="Terminal"
$ terraform apply -auto-approve
No changes. Your infrastructure matches the configuration.
Apply complete! Resources: 0 added, 0 changed, 0 destroyed.
```

### Catching drift with check mode
- Someone edits `resolv.conf` by hand to point at a public resolver
- `--check` is Ansible's ==check mode==, a ==dry run==: it predicts changes without making them; `--diff` shows the lines

```console label="Terminal"
$ ansible-playbook site.yml --check --diff
TASK [Resolver points at internal DNS] ********
--- before: etc/resolv.conf
+++ after: etc/resolv.conf
@@ -1 +1 @@
-nameserver 8.8.8.8
+nameserver 10.0.0.53

changed: [localhost]
```

- Check mode leaves the file alone; a normal run puts it back. `changed=0` on a scheduled check means no drift

### Writing idempotent code yourself
- Imperative scripts can be idempotent; you add the ==guard checks==
  - Look before you act; prefer `mkdir -p`, `ln -sf`, and writing a whole file over appending with `>>`

```bash label="add-dns-safe.sh"
#!/usr/bin/env bash
# Check the current state before acting
set -euo pipefail
mkdir -p etc
line="nameserver 10.0.0.53"
grep -qxF "$line" etc/resolv.conf 2>/dev/null ||
  echo "$line" >> etc/resolv.conf
```

- In Ansible, prefer a module over `command` or `shell`
  - Ansible cannot know what a command did, so it reports ==changed== on every run
  - Guard commands with `creates:` or `removes:` (skip if a file exists or is absent), or set `changed_when:`

```yaml label="cmd.yml (tasks)"
- name: Append with shell
  ansible.builtin.shell: echo "vlan 10" >> vlans.txt

- name: Generate an API token once
  ansible.builtin.command:
    cmd: openssl rand -hex -out api.token 16
    creates: api.token
```

```console label="ansible-playbook cmd.yml (second run)"
TASK [Append with shell] **********************
changed: [localhost]

TASK [Generate an API token once] *************
ok: [localhost]
```

- The same word applies to APIs (objective 2.3)
  - `GET`, `PUT`, and `DELETE` are idempotent by definition; `POST` is not, so a retried `POST` can create a duplicate

:::exam
- "Running the playbook again makes no further changes" or "safe to run repeatedly" means idempotent. "Describe the desired end state and let the tool decide the steps" means declarative.
- Ansible `shell` and `command` tasks report changed every run unless guarded with `creates`, `removes`, or `changed_when`. Replacing them with a purpose-built module is the usual fix.
- Do not assume imperative means non-idempotent: a script that checks state before acting can be idempotent too.
:::
