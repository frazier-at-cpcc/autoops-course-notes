### CLI configuration
- Automation reaches a cloud provider through its ==command-line interface (CLI)==, a ==software development kit (SDK)==, or the raw API
  - Same question for all three: where does the credential come from, how long does it live, what may it do?
  - Worst: long-lived keys in scripts. Best: short-lived credentials issued to a ==machine identity==
- `aws configure` writes two plain-text files
  - `~/.aws/credentials`: secrets, one section per profile
  - `~/.aws/config`: region, output, roles, SSO settings
  - Section names differ: `[lab]` in credentials, `[profile lab]` in config
- Pick a profile with `--profile lab` or `AWS_PROFILE=lab`
- Environment variables: `AWS_ACCESS_KEY_ID`, `AWS_SECRET_ACCESS_KEY`, `AWS_SESSION_TOKEN`, `AWS_REGION`
  - `AWS_CONFIG_FILE` and `AWS_SHARED_CREDENTIALS_FILE` move the files, which keeps tests and CI isolated

```ini label="~/.aws/config"
[default]
region = us-east-1

[profile lab]
region = us-west-2

[profile deployer]
role_arn = arn:aws:iam::111122223333:role/deploy
source_profile = lab
```

```ini label="~/.aws/credentials (dummy keys)"
[default]
aws_access_key_id = AKIAIOSFODNN7EXAMPLE
aws_secret_access_key = dummy-secret-1

[lab]
aws_access_key_id = AKIAI44QH8DHBEXAMPLE
aws_secret_access_key = dummy-secret-2
```

- ==Precedence==, highest first: command-line options, environment variables, role and SSO settings in the profile, `~/.aws/credentials`, `~/.aws/config`, container role, EC2 instance profile
  - `aws configure list` shows which source won for each value
  - For people, `aws configure sso` plus `aws sso login` gives short-lived credentials and leaves no secret on disk

:::wide
```console label="Terminal"
$ AWS_REGION=eu-west-1 aws configure list --profile lab
NAME       : VALUE                    : TYPE             : LOCATION
profile    : lab                      : manual           : --profile
access_key : ****************MPLE     : shared-credentials-file :
secret_key : ****************et-2     : shared-credentials-file :
region     : eu-west-1                : env              : ['AWS_REGION', 'AWS_DEFAULT_REGION']
```

| Task | AWS CLI | Azure CLI | Google Cloud CLI |
|---|---|---|---|
| Person signs in | `aws sso login` | `az login` | `gcloud auth login` |
| Settings folder | `~/.aws/` (`AWS_CONFIG_FILE`) | `~/.azure/` (`AZURE_CONFIG_DIR`) | `~/.config/gcloud/` (`CLOUDSDK_CONFIG`) |
| Named settings | profiles: `--profile`, `AWS_PROFILE` | subscriptions: `az account set --subscription` | configurations: `gcloud config configurations activate` |
| Machine signs in | instance profile or role | `az login --identity` or `--service-principal` | attached service account, `gcloud auth activate-service-account` |
| SDK default chain | env, profiles, container or instance role | `DefaultAzureCredential`: env, workload identity, managed identity, CLI sign-in | ==Application Default Credentials==: `GOOGLE_APPLICATION_CREDENTIALS`, gcloud ADC file, metadata server |
:::

### SDK credential chains
- An SDK walks a ==credential provider chain== and uses the first source that answers
  - Same code on a laptop (profile), in CI (federated token), and on a server (instance role)
  - Never put keys in the client constructor; they end up in Git
- boto3 checks code arguments, then environment variables, then profiles, then container and instance roles
  - An explicit `profile_name` beats keys in the environment; `AWS_PROFILE` does not

```python label="chain.py"
# chain.py: which provider supplied credentials?
import boto3

for profile in (None, "lab", "deployer"):
    s = boto3.Session(profile_name=profile)
    c = s.get_credentials()
    print(f"{profile or '(none)':9} {c.method}")
```

```console label="Offline run with dummy keys"
$ python3 chain.py
(none)    shared-credentials-file
lab       shared-credentials-file
deployer  assume-role
$ export AWS_ACCESS_KEY_ID=AKIAI44QH8DHBEXAMPLE
$ export AWS_SECRET_ACCESS_KEY=dummy-secret-3
$ python3 chain.py
(none)    env
lab       shared-credentials-file
deployer  assume-role
```

- `assume-role` is lazy: boto3 calls STS only when the keys are first used

### IAM and least privilege
- ==Identity and Access Management (IAM)==: who may call which API on which resource, under which conditions
- ==Least privilege==: only the actions and resources the job needs
  - A job that reads switch backups needs `s3:GetObject` on one prefix, not `s3:*` on `*`
  - One identity per job, so one leaked credential opens one door
- Lint policies in the pipeline: `parliament` flags `s3:*` on `*`, and an object action aimed at a bucket ARN

```json label="s3-read.json"
{
  "Version": "2012-10-17",
  "Statement": [
    {"Sid": "ReadBackups", "Effect": "Allow",
     "Action": "s3:GetObject",
     "Resource": "arn:aws:s3:::net-backups/cfg/*"},
    {"Sid": "ListThatPrefix", "Effect": "Allow",
     "Action": "s3:ListBucket",
     "Resource": "arn:aws:s3:::net-backups",
     "Condition": {"StringLike":
       {"s3:prefix": "cfg/*"}}}
  ]
}
```

```console label="parliament (IAM policy linter)"
$ parliament --minimal < too-broad.json
RESOURCE_STAR
$ parliament --minimal < wrong-arn.json
RESOURCE_MISMATCH
$ parliament --minimal < s3-read.json; echo $?
0
```

### Machine identities and federation
- A ==machine identity== belongs to a workload, not a person
  - The platform issues short-lived credentials and rotates them; nothing is stored on disk

| Platform | Machine identity |
|---|---|
| AWS EC2 | instance profile (an IAM role) via IMDSv2 |
| AWS ECS, EKS | task role; EKS Pod Identity or IRSA |
| Azure | managed identity, system- or user-assigned |
| Google Cloud | attached service account |
| CI, other clouds | ==workload identity federation== |

- Federation: the outside workload presents an ==OpenID Connect (OIDC)== token instead of a stored key
  - AWS: IAM OIDC provider plus a role trust policy; Azure: federated credential; Google Cloud: workload identity pool

```yaml label="deploy.yml (actionlint: OK)"
permissions:
  id-token: write  # lets the job request a JWT
  contents: read
jobs:
  deploy:
    runs-on: ubuntu-latest
    environment: production
    steps:
    - uses: aws-actions/configure-aws-credentials@v6
      with:
        role-to-assume: ${{ vars.DEPLOY_ROLE_ARN }}
        aws-region: us-east-1
    - run: aws sts get-caller-identity
```

- The role's ==trust policy== allows `sts:AssumeRoleWithWebIdentity` only when the token's claims match
  - `aud` (audience): `sts.amazonaws.com`
  - `sub` (subject): `repo:cpcc-netops/site:environment:production`
  - Leave out the `sub` check and any GitHub repository could assume the role

:::figure wide 4.3-oidc-federation.svg | GitHub Actions to AWS with no stored secret. The trust policy decides which repository, branch, or environment may assume the role.

### Accessing external APIs

:::wide
| | API key | OAuth 2.0 client credentials |
|---|---|---|
| Sent with each call | the same static key, in a header such as `X-API-Key` | a short-lived access token in `Authorization: Bearer` |
| How it is obtained | copied from the provider's console | client ID and secret posted to the token endpoint with `grant_type=client_credentials` |
| Lifetime and scope | until revoked; often all-or-nothing | minutes to an hour; scopes requested per token |
:::

- Keep either in a secrets manager (Vault, AWS Secrets Manager, Azure Key Vault), never in the repository
- ==Key rotation==: replace credentials on a schedule, and at once after any exposure
  - An AWS IAM user may hold two access keys, so rotation has no gap: create the new key, deploy it, deactivate the old one, then delete it
  - `GetAccessKeyLastUsed` finds keys nobody uses any more
  - Machine identities and short-lived tokens remove most rotation work

:::exam
- "No long-lived credentials in the pipeline" points to OIDC federation (workload identity) or a machine identity, not a better-protected access key.
- CLI precedence: command-line options beat environment variables, which beat the shared files; instance and container roles are the fallback.
- An API key is static until revoked; OAuth client credentials trade a client secret for short-lived, scoped tokens.
:::
