### Quality assurance in the delivery pipeline
- ==Quality assurance (QA) testing== proves a build is fit to release before users depend on it
- Each kind of test is a ==gate==: a failure stops the pipeline
  - Cheap, fast tests run first on every commit; slow, expensive ones run later on fewer builds
- After the deploy, ==validation== confirms the release works where it runs; ==remediation== is what you do when it does not

:::figure wide 4.1-validation-gates.svg | Where each check runs. Every yellow box can stop the pipeline; checks after the production deploy trigger a rollback instead.

| Test | Question it answers |
|---|---|
| Unit | does this function work alone? |
| Integration | do the parts work together? |
| Regression | did an old bug come back? |
| Load | does it hold up at expected traffic? |
| Smoke | is the new deploy alive at all? |
| Post-deployment | is production healthy now? |

### Integration and regression testing
- ==Integration testing== runs components together with their real dependencies
  - The app against a real PostgreSQL, Redis, or message queue instead of a mock
  - CI starts the dependencies as containers: GitLab `services:`, GitHub Actions service containers, `docker compose up`
  - An Ansible role tested against a throwaway VM or container (Molecule)
- ==Regression testing== reruns the existing suite after every change
  - When a bug is fixed, a test that reproduces it joins the suite
  - The bug can never return quietly: if it does, that test fails

```python label="test_vlans.py"
from vlans import parse_vlans

def test_single():
    assert parse_vlans("10") == [10]

def test_range():
    assert parse_vlans("20-22") == [20, 21, 22]

# NET-311: a trailing comma crashed the parser
def test_trailing_comma():
    assert parse_vlans("10,20,") == [10, 20]
```

```console label="Before and after the fix"
$ pytest -q --tb=no -rN
..F                              [100%]
1 failed, 2 passed in 0.01s
$ pytest -q --tb=no -rN
...                              [100%]
3 passed in 0.01s
```

### Load testing
- ==Load testing== sends a realistic volume of requests and measures the response
  - Throughput (requests per second), ==latency percentiles== (p95, p99), error rate
  - Averages hide the slow tail; the p99 is what your unluckiest users feel
- Related tests
  - Stress: push past expected load to find the breaking point
  - Soak: hold normal load for hours to expose memory leaks
  - Spike: jump from idle to peak at once
- Run against staging that matches production size, never against production without a plan
- Tools: `ab` (ApacheBench), `hey`, `k6`, JMeter, Locust
  - k6 `thresholds` such as `p(95)<200` fail the run, which fails the pipeline stage
- In the `ab` output below, the last block is the latency percentiles in milliseconds

### Smoke tests and post-deployment testing
- ==Smoke testing==: a short check run right after a deploy
  - Does the service answer, is the right version live, is it fast enough?
  - Seconds, not minutes; it does not prove every feature
- The exit code is the gate: `0` passes, anything else fails the pipeline step

```sh label="smoke.sh"
#!/bin/sh
# Usage: ./smoke.sh BASE_URL EXPECTED_VERSION
base=$1 want=$2 rc=0
ok()  { echo "PASS  $1"; }
bad() { echo "FAIL  $1"; rc=1; }

code=$(curl -s -o /dev/null -m 5 \
  -w '%{http_code}' "$base/healthz")
if [ "$code" = 200 ]; then ok "healthz 200"
else bad "healthz returned $code"; fi

ver=$(curl -s -m 5 "$base/version")
if [ "$ver" = "$want" ]; then ok "version $ver"
else bad "version $ver, want $want"; fi

t=$(curl -s -o /dev/null -m 5 \
  -w '%{time_total}' "$base/")
if awk "BEGIN{exit !($t < 0.5)}"; then
  ok "home page in ${t}s"
else bad "home page took ${t}s"; fi
exit $rc
```

```console label="A good deploy, then a broken one"
$ ./smoke.sh http://127.0.0.1:18451 2.1.1
PASS  healthz 200
PASS  version 2.1.1
PASS  home page in 0.000952s
$ echo $?
0
$ ./smoke.sh http://127.0.0.1:18452 2.1.1
FAIL  healthz returned 503
FAIL  version 2.1.0, want 2.1.1
PASS  home page in 0.001103s
$ echo $?
1
```

- ==Post-deployment testing== keeps checking production after the smoke test passes
  - Synthetic monitoring: scripted user journeys every minute from several regions
  - Compare error rate and latency with the previous version
  - A failed check triggers ==automatic rollback== or pages the on-call engineer

```yaml label=".github/workflows/deploy.yml (actionlint: OK)"
    steps:
      - uses: actions/checkout@v6
      - name: Deploy to the idle color
        run: ./switch.sh green
      - name: Smoke test (gate)
        run: ./smoke.sh "$APP_URL" "${TAG#v}"
        env:
          APP_URL: https://app.example.com
          TAG: ${{ github.ref_name }}
      - name: Roll back on failure
        if: failure()
        run: ./switch.sh blue
```

### Hotfixes
- A ==hotfix== is an urgent fix to the version running in production
  - Outage, security hole, data corruption: it cannot wait for the next planned release
- Branch from the release that is live, not from `main`
  - `main` already holds unreleased features you do not want to ship tonight
  - This is the release branch model from objective 1.2: the fix lands on `release/2.1` and ships as patch `v2.1.1`
- Same pipeline, shorter queue
  - Expedited review, but never skip the tests and smoke gate; a rushed fix is how one outage becomes two
- Carry the fix back to `main`, or the next release brings the bug back

```console label="Terminal"
$ git switch -c hotfix/NET-207 release/2.1
Switched to a new branch 'hotfix/NET-207'
$ sed -i 's/ttl 3$/ttl 300/' zone.conf
$ git commit -qam "fix(dns): restore TTL"
$ git switch -q release/2.1
$ git merge --no-ff --no-edit hotfix/NET-207
Merge made by the 'ort' strategy.
 zone.conf | 2 +-
 1 file changed, 1 insertion(+), 1 deletion(-)
$ git tag -a v2.1.1 -m "Hotfix: zone TTL"
$ git switch -q main
$ git cherry-pick -x hotfix/NET-207
[main f0b3af7] fix(dns): restore TTL
 1 file changed, 1 insertion(+), 1 deletion(-)
```

- Remediation options, fastest first: roll back, turn off a feature flag, ship a hotfix
  - Roll back first if you can; fix forward when rollback is impossible (a database migration already ran)

:::exam
- "Verify the critical functions right after deployment" is a smoke test. "A fixed bug reappeared" calls for regression testing. "Will it handle Black Friday traffic" is load testing.
- Integration testing checks components together; a distractor will describe unit testing of one function in isolation.
- A hotfix branches from the production release, not from `main`, and must be merged back.
:::
