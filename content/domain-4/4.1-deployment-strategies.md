### From pipeline to production
- ==Continuous delivery== (CD): every change that passes the pipeline is ready to release
  - A person approves the production step; ==continuous deployment== removes that approval
- A ==delivery method== decides how the new version replaces the old one
  - How many users see it first, whether anything goes down, how fast you can undo it
- Four methods to know: in-place, rolling, blue-green, canary
  - All four can be automated: AWS CodeDeploy, Kubernetes, Argo Rollouts, Ansible, a load balancer API

:::figure wide 4.1-deployment-strategies.svg | The same four-server service under each delivery method. Purple boxes run the new version; rust boxes are being replaced.

### In-place and rolling
- ==In-place== deployment: stop the app on the existing servers, install the new version, start it again
  - No new infrastructure; the cheapest method
  - Users see an outage while the service restarts
  - Rollback means running the old deployment again, which takes as long as the bad one did
  - Kubernetes calls this the `Recreate` strategy
- ==Rolling== deployment: replace instances in batches
  - The load balancer drains a batch, the batch upgrades, passes its health check, and rejoins
  - No full outage, but capacity drops by one batch at a time
  - Old and new versions serve traffic together until the last batch finishes, so both must work with the same database schema and API
  - Rollback is another rolling deployment, in the other direction
- Kubernetes `Deployment` objects roll by default
  - `maxUnavailable`: how many pods may be down during the update
  - `maxSurge`: how many extra pods may be created above `replicas`
  - Both default to 25%
  - A `readinessProbe` keeps traffic away from a pod until it answers

```yaml label="deploy.yaml (excerpt)"
spec:
  replicas: 4
  strategy:
    type: RollingUpdate
    rollingUpdate:
      maxUnavailable: 1  # at most 1 pod down
      maxSurge: 1        # at most 1 extra pod
```

### Blue-green
- Two identical production environments
  - ==Blue== serves users; ==green== sits idle with the new version installed
- Test green with production configuration while nobody uses it
- Cut over by repointing the router: load balancer target group, reverse proxy upstream, or DNS record
- ==Rollback== is the same switch in reverse, in seconds
  - Keep blue running until green has proved itself
- Cost: double the capacity while both run
- Shared database is the hard part
  - Schema changes must work for blue and green until blue is retired
- DNS cutovers are slowed by caching; clients keep the old address until the TTL expires

```sh label="switch.sh"
#!/bin/sh
# Usage: ./switch.sh blue|green
# $PROXY is the proxy container's name
set -e
cat > conf.d/upstream.conf <<CONF
upstream app {
    server $1:80;
}
CONF
docker exec "$PROXY" nginx -t -q
docker exec "$PROXY" nginx -s reload
```

- The demo: an nginx proxy on port 18450 in front of two app containers that answer `v1 blue` and `v2 green`
  - `traffic.sh` sends a request every 10 ms and prints the body and HTTP status
- `nginx -s reload` starts new workers and lets old ones finish their requests, so no request fails

```console label="Terminal"
$ ./traffic.sh 300 > log.txt &
$ ./switch.sh green
$ wait; sort log.txt | uniq -c
    209 v1 blue 200
     91 v2 green 200
$ ./switch.sh blue
$ curl -s http://127.0.0.1:18450/
v1 blue
```

### Canary
- Send a small share of real traffic to the new version first
  - Named for the canary that warned coal miners of bad air
- Watch the canary's error rate and latency against the old version's
  - Healthy: raise the share in steps (10%, 25%, 50%, 100%)
  - Unhealthy: set its share to zero; only that slice of users ever saw the problem
- Needs good monitoring and automation to judge each step
  - Argo Rollouts and Flagger automate the analysis in Kubernetes
  - AWS CodeDeploy has predefined canary and linear traffic-shifting configurations for Lambda and ECS
- Split by weight, or by user group (employees first, one region first)
- A ==feature flag== hides a feature inside code that is already deployed; a canary limits who reaches the new deployment

```nginx label="conf.d/upstream.conf"
upstream app {
    zone app 64k;
    server blue:80  weight=9;
    server green:80 weight=1;
}
```

```console label="Terminal"
$ ./traffic.sh 100 | sort | uniq -c
     90 v1 blue 200
     10 v2 green 200
```

### Choosing a method

:::wide
| Method | Downtime | Rollback | Extra cost |
|---|---|---|---|
| In-place | yes, while the app restarts | slow: redeploy the old version | none |
| Rolling | none; capacity dips one batch at a time | slow: roll back batch by batch | little (surge instances) |
| Blue-green | none; one switch moves everyone | fast: switch back | a full second environment |
| Canary | none; a small share sees v2 first | fast: send the share back to v1 | little (the canary instances) |
:::

- Mixed versions in production at once: rolling and canary
  - Design changes so both versions can run side by side
- Smallest blast radius: canary
- Fastest, simplest rollback: blue-green
- Lowest cost and simplest tooling: in-place, if a maintenance window is acceptable

Build the blue-green demo: two `nginx:1.27-alpine` containers on one Docker network, each with a `return 200 "v1 blue";` style location, and a third nginx with the upstream file above. Run `switch.sh` while a curl loop is running and confirm every line of the log ends in `200`.
:::

:::exam
- "Release to 5% of users and expand if metrics stay healthy" is canary. "Two identical environments and a router switch" is blue-green.
- "Instant rollback" points to blue-green; "lowest cost, downtime acceptable" points to in-place.
- Rolling and canary both run two versions at once; a question about schema or API compatibility during deployment is pointing at them.
:::
