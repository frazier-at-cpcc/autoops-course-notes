### Checks that make a pipeline worth trusting
- A pipeline that only builds and deploys ships bugs and vulnerabilities faster
- ==Pipeline-enhancing concepts== add automated checks between commit and deploy
  - ==Security scanning==: code, dependencies, images, secrets
  - Code quality scanning: style, complexity, duplication, test coverage
  - ==Containerization==: every job runs in a known, pinned environment
  - AI-based log analysis: help reading a failed job's output
- Each scanner becomes a ==gate==: a non-zero exit code fails the job and blocks the merge or deploy
- Run the cheap checks first; a 5-second linter should not wait behind a 10-minute image build

:::wide
| Scan | What it reads | Finds | Example tools |
|---|---|---|---|
| SAST (static application security testing) | your source code | injection, unsafe calls, hardcoded passwords | Bandit, Semgrep, CodeQL |
| SCA / dependency scanning | lock and requirements files | libraries with known CVEs, license issues | Trivy, Grype, pip-audit, Dependabot |
| Container image scanning | OS packages and libraries inside an image | CVEs in the base image and installed packages | Trivy, Grype, Clair |
| Secret scanning | files and Git history | API keys, tokens, private keys | gitleaks, TruffleHog, push protection |
| IaC scanning | Terraform, Kubernetes, Dockerfiles | misconfigurations such as public buckets | Checkov, Trivy config, tfsec |
| DAST (dynamic testing) | the running application | issues visible from outside | OWASP ZAP |
:::

### Static and dependency scanning
- ==SAST== reads source code without running it, like a linter with a security rule set
- Bandit (Python) on a backup script: every finding has a test ID and a severity

```python label="backup.py"
import subprocess

PASSWORD = "Sw1tch!Adm1n"


def backup(host):
    cmd = f"scp admin@{host}:running-config ."
    subprocess.run(cmd, shell=True)
```

```console label="Terminal"
$ bandit -q -f custom \
    --msg-template '{line}:{test_id}:{severity}' \
    backup.py
1:B404:LOW
3:B105:LOW
8:B602:HIGH
$ echo $?
1
```

- `B602`: `subprocess` with `shell=True`; a host name like `x; rm -rf /` becomes a command
- `B105`: hardcoded password; `B404`: importing `subprocess` at all (informational)
- ==Software composition analysis (SCA)== checks the libraries you depend on against vulnerability databases
  - Most of a modern application is other people's code
  - Also produces a software bill of materials (==SBOM==) in CycloneDX or SPDX format

```console label="Terminal"
$ cat requirements.txt
requests==2.19.1
PyYAML==5.3
$ trivy fs -q --scanners vuln \
    --severity HIGH,CRITICAL --format json . \
  | jq -r '.Results[].Vulnerabilities[] |
    [.PkgName, .InstalledVersion, .VulnerabilityID,
     .Severity, .FixedVersion] | join(" ")'
PyYAML 5.3 CVE-2020-14343 CRITICAL 5.4
PyYAML 5.3 CVE-2020-1747 CRITICAL 5.3.1
requests 2.19.1 CVE-2018-18074 HIGH 2.20.0
```

- The fix column is the action: raise the pin to that version or later, then rerun

### Container image and secret scanning
- ==Container image scanning==: an image carries a whole OS userland, and every package in it can have CVEs
  - Scan after the build and before the push to the registry
  - Rebuild on a schedule; a clean image today has new CVEs next month
- `--exit-code 1` turns findings into a failing gate; `--severity` decides what counts

```console label="Terminal"
$ trivy image -q --severity CRITICAL --exit-code 1 \
    --format json alpine:3.14.0 > scan.json
$ echo $?
1
$ jq -r '.Results[].Vulnerabilities[] |
    [.PkgName, .VulnerabilityID, .FixedVersion]
    | join(" ")' scan.json
apk-tools CVE-2021-36159 2.12.6-r0
libcrypto1.1 CVE-2021-3711 1.1.1l-r0
libssl1.1 CVE-2021-3711 1.1.1l-r0
zlib CVE-2022-37434 1.2.12-r2
```

- Fix by moving to a newer base image tag, not by patching inside a running container
- ==Secret scanning== looks for credentials by known key formats and by entropy
  - In the pipeline as a backstop to the `pre-commit` hook (objective 1.2)
  - `gitleaks git` scans every commit in history; `gitleaks dir` scans files

```console label="Terminal"
$ gitleaks dir --no-banner --no-color -v .
Finding:     AKIAQX4ZL2RBWN3T6YUM
RuleID:      aws-access-token
File:        deploy.env
Line:        1
9:11AM WRN leaks found: 1
```

### Code quality scanning
- ==Code quality scanning== measures maintainability, not security
  - Linters and formatters in check mode: `ruff check`, `yamllint`, `ansible-lint`, `terraform fmt -check`
  - Complexity (deeply nested functions), duplicated code, ==test coverage==
- SonarQube (and SonarQube Cloud) collect these into one report per branch
  - A ==quality profile== is the rule set for each language
  - A ==quality gate== is the pass or fail condition, for example: coverage on new code at least 80%, no new critical issues, duplication under 3%
  - The pipeline step waits for the gate result and fails the job when the gate fails
- Gates usually judge new code only, so a legacy repository can adopt one without first fixing ten years of history
- GitLab shows Code Quality findings in the merge request; GitHub shows code scanning alerts on the pull request

### Containerization in the pipeline
- Each job runs inside a container image named in the pipeline file
  - GitLab `image:`; GitHub `container:` on a job or `docker://` for a step; Jenkins `agent { docker { image '...' } }`
- Why containerize build steps
  - ==Reproducible==: the same tool versions on every runner and on your laptop
  - ==Isolated==: one job cannot leave files or packages behind for the next
  - No hand-installed tools on runners; changing a version is a one-line change reviewed in Git
- Pin the tag (`trivy:0.57.1`, not `latest`), or the digest (`@sha256:...`) for full immutability
- A scan job that runs the scanner in its own image

```yaml label=".gitlab-ci.yml"
stages: [build, scan]

container-scan:
  stage: scan
  image:
    name: aquasec/trivy:0.57.1
    entrypoint: [""]
  variables:
    IMAGE: $CI_REGISTRY_IMAGE:$CI_COMMIT_SHA
  script:
    - trivy image --exit-code 1
      --severity CRITICAL "$IMAGE"
```

- `entrypoint: [""]` clears the image's own entrypoint so the runner can start a shell
- Building images inside CI: Docker-in-Docker (a privileged `docker:dind` service), or daemonless and rootless builders such as Buildah or rootless BuildKit
- `services:` start helper containers (a database, a mock API) next to the job

### AI-based log analysis
- A failed job can leave thousands of log lines; the real error is often one line near the middle
- ==Artificial intelligence (AI)-based log analysis== uses a language model or anomaly detection to
  - Summarize why the job failed and point to the lines that matter
  - Group repeated failures across runs (the same flaky test every Tuesday)
  - Suggest a likely fix: a missing dependency, a renamed variable, an expired token
- Built into platforms: GitLab Duo Root Cause Analysis on a failed job, Copilot explaining a failed GitHub Actions job; log platforms add anomaly detection
- Limits

| Concern | What to do |
|---|---|
| Confident but wrong answers | check the cited log line yourself |
| Long logs truncated | send the failing step, not the whole run |
| Secrets in logs | mask CI variables before logs leave |
| Different answer each run | treat it as a hint, not evidence |

- ==Human in the loop==: the model suggests, an engineer decides
  - Never let a model's suggestion change production or retry a deploy by itself
  - Masked CI/CD variables (GitLab prints `[MASKED]`) and `secrets.*` (GitHub prints `***`) keep credentials out of the text being analyzed

:::exam
- Match the scan to the artifact: source code is SAST, dependencies are SCA, a built image is container scanning, keys in files or history are secret scanning, and a running app is DAST.
- A quality gate fails the pipeline when a threshold is not met (coverage, new critical issues). A "pin the toolchain so every runner behaves the same" scenario points to running the job in a container image.
- AI-based log analysis speeds up diagnosis, but its output is a suggestion that a person verifies; watch for answers that let it act on production unreviewed.
:::

Install Bandit with `pip install bandit`, save `backup.py`, and run the scan. :::
