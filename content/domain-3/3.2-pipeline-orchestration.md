### Pipelines, stages, jobs, and steps
- A ==pipeline== is the full automated run that a trigger starts
- A ==stage== is a named phase: `lint`, `test`, `build`, `deploy`
- A ==job== is one unit of work inside a stage
  - Gets its own runner (GitLab) or runner machine (GitHub), starts from a clean workspace
  - A job passes or fails as a whole
- A ==step== is one command or action inside a job
  - Steps in a job share the same workspace and run in order
- ==Orchestration techniques== are the rules that decide
  - Which jobs run, in what order, and how many at once
  - What happens when one of them fails
- Same ideas, different words
  - Jenkins: a pipeline has `stages`, each stage has `steps`; one agent and one workspace unless you say otherwise
  - GitHub Actions: a workflow has `jobs`, each job has `steps`; no stage keyword

### Parallel vs. sequential
- ==Sequential==: each piece waits for the one before it
  - Stages always run in order; stage 2 starts only after every job in stage 1 passes
  - Safe and easy to read, but the pipeline is as slow as the sum of its parts
- ==Parallel==: independent jobs run at the same time
  - Jobs in the same stage run in parallel when runners are free
  - Lint the YAML and lint the Python at once; neither needs the other
- A ==matrix== fans one job out into many parallel copies
  - GitHub: `strategy.matrix`; GitLab: `parallel: matrix:`; Jenkins: a `matrix` or `parallel` block
  - One test job per site, OS, or Python version
- Matrix controls
  - `fail-fast: false` keeps the other copies running when one fails (GitHub defaults to `true`)
  - `max-parallel` caps how many run at once, so you do not hit 40 switches at the same moment
- Parallel is capped by runner capacity: ten jobs on two runners still run two at a time

### Step dependencies
- Stage order alone is coarse: one slow test job holds back every job in the next stage
- `needs:` declares the real ==dependencies== between jobs
  - A job starts the moment the jobs it needs succeed, whatever stage it is in
  - The jobs and their `needs` form a ==directed acyclic graph (DAG)==: arrows point one way and never loop back
  - `needs: []` starts a job immediately, with no dependencies
- GitHub uses the same keyword: `needs: build` or `needs: [lint, unit]`
- Jenkins runs stages in order; use a `parallel` block for branches of work

```yaml label=".gitlab-ci.yml (part 1)"
stages: [lint, test, build, deploy]

lint-yaml:
  stage: lint
  script: [echo "inventory ok"]

lint-python:
  stage: lint
  script: [echo "ruff ok"]

unit-tests:
  stage: test
  needs: [lint-python]
  script: [sleep 3, echo "14 passed"]

smoke-test:
  stage: test
  needs: [lint-yaml]
  allow_failure: true
  script: [exit 1]

render-configs:
  stage: build
  needs: [lint-yaml]
  script: [echo "rendered 12 configs"]
```

### Conditional execution
- ==Conditional execution== decides whether a job runs at all for this pipeline
- GitLab: `rules:` evaluated top to bottom; the first match wins
  - `if:` tests variables: `$CI_COMMIT_BRANCH == "main"`
  - `changes:` runs only when matching files changed: `changes: [inventory/**/*]`
  - Each rule can set `when:` (`on_success`, `manual`, `on_failure`, `never`); no match means the job is left out
- GitHub: `if:` on a job or step
  - `if: github.ref == 'refs/heads/main'`
  - ==Status functions==: `success()` (the default), `failure()`, `always()`, `cancelled()`
- Jenkins: a `when` block on a stage: `when { branch 'main' }`, `when { buildingTag() }`
- On a feature branch, the deploy rules evaluate to `never`

```console label="Terminal"
$ git switch -c feature/NET-200-acl
$ gitlab-ci-local --list-json \
    | jq -r '.[] | "\(.name) \(.when)"'
lint-yaml on_success
lint-python on_success
unit-tests on_success
smoke-test on_success
render-configs on_success
deploy-staging never
rollback never
```

### Failure handling
- Default behavior: a failed job fails the pipeline and later jobs that depend on it do not run
- Tolerate a known-flaky or advisory job
  - GitLab `allow_failure: true`: the job shows a warning (`WARN` above) and the pipeline continues
  - GitHub `continue-on-error: true` on a step or a job
- ==Retries== for failures that are not your code's fault
  - GitLab `retry: 2`, or `retry: {max: 2, when: runner_system_failure}`
  - Jenkins `retry(3) { ... }`; GitHub has no retry keyword (re-run the job, or retry inside the script)
  - Never retry a failing test until it passes; that hides a real bug
- ==Timeouts== stop a hung job from holding a runner for hours
  - GitHub's default `timeout-minutes` is 360; set your own
- Cleanup and notification jobs run on failure or always (table below)

:::wide
| Need | GitLab CI | GitHub Actions | Jenkins (declarative) |
|---|---|---|---|
| Keep going after a failure | `allow_failure: true` | `continue-on-error: true` | `catchError` / `unstable` |
| Retry | `retry: 2` | re-run job | `retry(3)` |
| Time limit | `timeout: 10m` | `timeout-minutes: 10` | `timeout(...)` in `options` |
| Run only after a failure | `when: on_failure` | `if: failure()` | `post { failure { } }` |
| Always run (cleanup) | `when: always` | `if: always()` | `post { always { } }` |
:::

### Automated rollbacks
- An ==automated rollback== returns production to the ==last known good== state without a person typing commands at 2 a.m.
- The pipeline detects the failure
  - The deploy command exits non-zero, or a post-deploy health check or smoke test fails
- The pipeline reacts with a job that runs only on failure

```yaml label=".gitlab-ci.yml (part 2)"
deploy-staging:
  stage: deploy
  needs: [unit-tests, render-configs]
  timeout: 10m
  rules:
    - if: $CI_COMMIT_BRANCH == "main"
  script:
    - echo "pushing configs"
    - test "$BREAK_DEPLOY" != "yes"

rollback:
  stage: deploy
  needs: [deploy-staging]
  rules:
    - if: $CI_COMMIT_BRANCH == "main"
      when: on_failure
  script: [echo "restoring last good configs"]
```

```console label="Terminal"
$ gitlab-ci-local --variable BREAK_DEPLOY=yes
deploy-staging $ test "$BREAK_DEPLOY" != "yes"
deploy-staging finished in 12 ms  FAIL 1
rollback       > restoring last good configs
 PASS  rollback
 FAIL  deploy-staging
```

- The same pattern in GitHub Actions: a `rollback` job with `needs: deploy` and `if: failure()`
  - With `act`, a failed deploy shows `deploy failure` then `rollback success`
- Rollback needs something to roll back to
  - Versioned, immutable artifacts: redeploy build `v1.3.2`, never "rebuild the old code"
  - Kubernetes: `kubectl rollout undo`; Helm 4: `helm upgrade --rollback-on-failure` (Helm 3 called it `--atomic`)
  - Blue/green: switch traffic back to the old environment
  - Network devices: Junos `commit confirmed 5` reverts unless confirmed; Cisco `configure replace` to an archived config
- Database schema changes are the hard case: make migrations backward compatible so old code still runs

:::exam
- "Run independent jobs at the same time to shorten the pipeline" is parallel execution; "start a job as soon as the specific jobs it depends on finish" is `needs` (a DAG), not stage order.
- Match the keyword to the behavior: `allow_failure` / `continue-on-error` tolerate a failure, `retry` repeats on transient errors, `timeout` limits a hung job, and `when: on_failure` / `if: failure()` / `post { failure }` run rollback or alert jobs.
- A scenario where a job never ran on a feature branch usually points to a `rules`, `if`, or `when` condition, not a broken script.
:::
