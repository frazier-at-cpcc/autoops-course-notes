### Hooks and triggers
- A ==pipeline trigger== is the event that starts a pipeline
  - Push, merge request, tag, schedule, a button, an API call, a chat command, another pipeline
- A ==webhook== is an HTTP POST the Git platform sends to a URL you register when an event happens
  - Push-based: the CI server hears about the commit within seconds
  - The alternative is ==polling== (Jenkins `pollSCM`): ask the repository every few minutes; slower and wasteful
- GitHub Actions and GitLab CI run inside the platform; external CI (Jenkins, a deploy tool, a chat bot) needs a real webhook
- Webhook request: headers name the event, the body is JSON describing it
  - GitHub: `X-GitHub-Event: push`, `X-GitHub-Delivery` (unique ID), `X-Hub-Signature-256`
  - GitLab: `X-Gitlab-Event: Push Hook`; `X-Gitlab-Token` (shared secret in plain text) or, from GitLab 19.0, an HMAC `webhook-signature`

:::figure wide 3.3-webhook-flow.svg | The receiver recomputes the signature from the raw body and its own copy of the secret. A forged or altered request fails the comparison and nothing runs.

### Verifying a signed webhook
- Anyone who finds the URL can POST to it, so the receiver must prove the request came from the platform
- GitHub signs the raw body with ==HMAC-SHA256== using a secret you set on the webhook
  - Header: `X-Hub-Signature-256: sha256=<hex digest>`
  - The receiver computes the same HMAC and compares with a ==constant-time comparison== (`hmac.compare_digest`) so timing does not leak the answer
```python label="hook.py"
import hashlib
import hmac
import os
from http.server import BaseHTTPRequestHandler
from http.server import HTTPServer

SECRET = os.environ["WEBHOOK_SECRET"].encode()


class Hook(BaseHTTPRequestHandler):
    def do_POST(self):
        size = int(self.headers["Content-Length"])
        body = self.rfile.read(size)
        mac = hmac.new(SECRET, body, hashlib.sha256)
        want = "sha256=" + mac.hexdigest()
        got = self.headers.get(
            "X-Hub-Signature-256", "")
        ok = hmac.compare_digest(want, got)
        # 202: queue the pipeline; 401: drop it
        self.send_response(202 if ok else 401)
        self.end_headers()


server = HTTPServer(("127.0.0.1", 18400), Hook)
server.serve_forever()
```

```console label="Terminal"
$ export WEBHOOK_SECRET='lab-only-secret'
$ python3 hook.py &
$ BODY='{"ref":"refs/heads/main"}'
$ SIG=$(printf '%s' "$BODY" | openssl dgst \
    -sha256 -hmac "$WEBHOOK_SECRET" -r | cut -c1-64)
$ post() { curl -s -o /dev/null -w '%{http_code}\n' \
    -H "X-Hub-Signature-256: sha256=$SIG" \
    -d "$1" http://127.0.0.1:18400/; }
$ post "$BODY"
202
$ post '{"ref":"refs/heads/evil"}'
401
```

- Same signature, one changed byte in the body: rejected
- Also: answer fast (queue the work, return `202`), use HTTPS, and ignore repeated delivery IDs

### ChatOps
- ==ChatOps== (==chat-based operations==) runs operations from a chat channel: a command in Slack, Teams, or Mattermost starts a pipeline job, and the result is posted back
  - The channel becomes a shared, searchable log of who ran what and what happened
  - Suited to routine, low-risk actions: show VLANs, check a deploy status
- GitLab ChatOps: `/gitlab netops/configs run show-vlans core-sw1`
  - Runs the named job from the default branch with `CI_PIPELINE_SOURCE` set to `chat`
  - Arguments arrive in `CHAT_INPUT`; also `CHAT_CHANNEL` and `CHAT_USER_ID`
  - Needs the Developer role or higher on the project
- Other platforms: a bot (Hubot, Errbot, a Slack app) that calls the CI API, often with an approval step
- Treat chat commands like any other access: least privilege, audit log, no secrets pasted into the channel

```yaml label=".gitlab-ci.yml (chat job)"
show-vlans:
  rules:
    - if: $CI_PIPELINE_SOURCE == "chat"
  script:
    - echo "VLANs on $CHAT_INPUT are 10 20 30"
```

```console label="Terminal"
$ gitlab-ci-local --variable CI_PIPELINE_SOURCE=chat \
  --variable CHAT_INPUT=core-sw1 show-vlans
show-vlans > VLANs on core-sw1 are 10 20 30
```

### Push, manual, and scheduled triggers
- ==Push trigger==: every push (or every push to listed branches, tags, or paths) starts the pipeline
- ==Manual trigger==: a person starts it, often with inputs; used for production deploys and one-off jobs
- ==Scheduled trigger==: a ==cron== expression starts it at set times; nightly backups, drift checks, image rescans

:::wide
| Trigger | GitHub Actions | GitLab CI | Jenkins |
|---|---|---|---|
| Push | `on: push` with `branches`, `tags`, `paths` | default; filter with `rules` | webhook, or `pollSCM('H/5 * * * *')` |
| Merge or pull request | `on: pull_request` | `$CI_PIPELINE_SOURCE == "merge_request_event"` | multibranch `CHANGE_ID` builds |
| Manual | `on: workflow_dispatch` with `inputs` | `when: manual` job; Run pipeline button | Build with Parameters; `input` step pauses |
| Scheduled | `on: schedule` with `cron` (UTC) | pipeline schedule in the UI; `$CI_PIPELINE_SOURCE == "schedule"` | `triggers { cron('H 2 * * *') }` |
:::

- Cron fields: `minute hour day-of-month month day-of-week`
  - `17 6 * * 1-5`: 06:17 Monday to Friday; `*/15 * * * *`: every 15 minutes; `0 2 1 * *`: 02:00 on the first of the month
  - Jenkins `H` picks a hashed minute so 50 jobs do not all start at :00
- GitHub schedules run on the default branch in UTC, no more often than every 5 minutes, and can start late when runners are busy

```yaml label=".github/workflows/netops.yml"
name: netops
on:
  push:
    branches: [main]
    tags: ['v*']
  schedule:
    - cron: '17 6 * * 1-5'
  workflow_dispatch:
    inputs:
      target:
        type: choice
        options: [staging, production]
        default: staging
jobs:
  info:
    runs-on: ubuntu-latest
    steps:
      - run: |
          echo "event=${{ github.event_name }}"
          echo "ref_name=${{ github.ref_name }}"
          echo "ref_type=${{ github.ref_type }}"
          echo "sha=${{ github.sha }}"
          echo "target=${{ inputs.target }}"
```

- `actionlint` catches a bad cron before GitHub silently ignores the schedule

```console label="Terminal"
$ actionlint bad.yml
bad.yml:7:13: invalid CRON format "0 25 * * *" in schedule event: end of range (25) above maximum (23): 25 [events]
```

### Git variables: tag, branch, commit
- Every run exposes ==Git variables== naming the ==ref== (branch or tag) and the commit that started it; jobs use these to name artifacts, tag images, and decide whether to deploy

:::wide
| Value | GitHub Actions | GitLab CI | Jenkins (multibranch) |
|---|---|---|---|
| Branch | `github.ref_name` when `github.ref_type` is `branch` | `CI_COMMIT_BRANCH` (not set in tag or merge request pipelines) | `BRANCH_NAME` |
| Tag | `github.ref_name` when `github.ref_type` is `tag` | `CI_COMMIT_TAG` (set only in tag pipelines) | `TAG_NAME` (tag builds only) |
| Commit | `github.sha` / `$GITHUB_SHA` | `CI_COMMIT_SHA`, `CI_COMMIT_SHORT_SHA` | `GIT_COMMIT` (Git plugin) |
| Branch or tag | `github.ref` (`refs/heads/main`) | `CI_COMMIT_REF_NAME` | `BRANCH_NAME` (holds the tag name in a tag build) |
:::

- The workflow above, run with `act` for a push of tag `v1.4.0` and for a manual run

```console label="Terminal"
$ act push -e tag.json --json \
  | jq -j 'select(.raw_output) | .msg'
event=push
ref_name=v1.4.0
ref_type=tag
sha=5772eca0b2b1196ba48b82018561690b38f5ca84
target=
$ act workflow_dispatch -e dispatch.json --json \
  | jq -j 'select(.raw_output) | .msg'
event=workflow_dispatch
ref_name=main
ref_type=branch
target=production
```

- GitLab, a job that echoes `CI_PIPELINE_SOURCE`, `CI_COMMIT_BRANCH`, `CI_COMMIT_TAG`, and `CI_COMMIT_SHA`, run for a push to `main` and for tag `v1.4.0`

```console label="Terminal"
$ gitlab-ci-local vars
vars > source=push
vars > branch=main
vars > tag=
vars > sha=448f0309d1aeb724b1da80315c08703adfd23bc4
$ gitlab-ci-local --variable CI_COMMIT_TAG=v1.4.0 \
    --unset-variable CI_COMMIT_BRANCH vars
vars > branch=
vars > tag=v1.4.0
```

- Jenkins multibranch build of tag `v1.4.0`: the `Release` stage runs `sh 'echo "release $TAG_NAME"'` and prints `release v1.4.0`; the `main` build prints the full `GIT_COMMIT`
- A rule that tests `CI_COMMIT_BRANCH == "main"` never matches in a tag pipeline; release jobs test `CI_COMMIT_TAG` instead

:::exam
- "Notify the external build server immediately when code is pushed" is a webhook; "check the repository every five minutes" is polling. A webhook receiver validates `X-Hub-Signature-256` (HMAC-SHA256 of the body with a shared secret).
- Know the trigger keywords: `on: push`, `workflow_dispatch` and `when: manual` (manual), `schedule` with cron (scheduled), and ChatOps for commands typed in chat.
- Read the variable for the ref type: a job that should run only for releases tests the tag (`CI_COMMIT_TAG`, `github.ref_type == 'tag'`, `TAG_NAME`), and it will be empty on a branch build.
:::
