### Artifacts and where they live
- An ==artifact== is anything a pipeline builds and keeps
  - Container images, Python wheels, npm packages, Ansible collection tarballs, Helm charts, Terraform modules, signed firmware bundles, test reports
- Build once, then promote the same artifact through test, staging, and production
  - Rebuilding for each stage means production runs something that was never tested
- An ==artifact registry== stores artifacts with names, versions, and access control
  - Pipelines push to it; deploy jobs and servers pull from it
- An ==external artifact repository== is one hosted outside your build system, by a vendor or a separate team
  - Also used as a ==proxy== or cache for public registries, so builds survive a Docker Hub rate limit or a deleted upstream package

| Repository | Holds |
|---|---|
| Docker Hub | public and private images |
| GitHub Packages (GHCR) | images, npm, Maven, NuGet |
| Sonatype Nexus | most formats, plus proxies |
| JFrog Artifactory | most formats, plus proxies |
| AWS ECR, Azure ACR, Google GAR | images in that cloud |

### Authentication and authorization
- ==Authentication==: who are you?
  - A password, a scoped access token, or a short-lived OIDC token from the CI platform
  - HTTP `401 Unauthorized` means the registry does not know who you are
- ==Authorization==: what may you do?
  - Pull, push, delete, or administer, per repository or project
  - HTTP `403 Forbidden` means it knows who you are and the answer is no
- The lab registry is `registry:2` (CNCF Distribution) with `htpasswd` users

```console label="Terminal"
$ REG=localhost:18352/netops/cfg-backup
$ curl -s -o /dev/null -w '%{http_code}\n' \
    http://localhost:18352/v2/_catalog
401
$ docker push $REG:1.4.0
...
push access denied, ... no basic auth credentials
$ echo 'Pipel1ne!' | docker login localhost:18352 \
    -u ci-bot --password-stdin
WARNING! Your credentials are stored unencrypted in '/tmp/tmp.1fG6coP3mo/docker/config.json'.
...
Login Succeeded
```

- That warning matters on shared runners
  - Configure a ==credential helper== (`docker-credential-pass`, `osxkeychain`, `wincred`, or a cloud helper), and `docker logout` at the end of the job
- Plain `registry:2` stops at authentication
  - In the test, a second account named `auditor` pushed a new tag without any trouble
  - Harbor, Nexus, Artifactory, and the cloud registries add roles: a CI robot account that can push to one project, and pull-only accounts for servers

### Versioning: tags and digests
- A ==tag== is a human-friendly name that points at an image: `1.4.0`, `1.4`, `latest`
  - Tags are ==mutable== by default: pushing the same tag again moves it
- A ==digest== is the SHA-256 hash of the image manifest: `sha256:d43a...`
  - Change one byte of content and the digest changes, so a digest always means the same image
- Version with semantic versioning tags; deploy by digest

```console label="Terminal"
$ V1=$(docker push $REG:1.4.0 \
    | awk '/digest:/{print $3}')
$ echo $V1
sha256:d43a49b3bbb5b75b35ef09deb88ed2...
```

- Edit `backup.sh` to print `backup v2`, rebuild, and push the same tag

```console label="Terminal"
$ docker push $REG:1.4.0 | awk '/digest:/{print $3}'
sha256:493ed42735d69488582c190b7240e3...
$ docker run --rm $REG:1.4.0
backup v2
$ docker run --rm $REG@$V1
backup v1
```

:::figure 3.1-tag-vs-digest.svg | Re-pushing 1.4.0 moved the tag to a new image. The digest still names the original, which the registry kept.

- `latest` is only a tag; nothing makes it the newest image
- Record the digest the build produced and pass it to the deploy job; Kubernetes manifests and Compose files accept `image@sha256:...`

### Immutability
- ==Immutability==: once a version is published, its contents never change
  - Same rule as SemVer: a fix is a new version, never a re-push
- Turn it on in the registry
  - Amazon ECR: tag mutability set to `IMMUTABLE`
  - Harbor: tag immutability rules per project
  - Artifactory and Nexus: release repositories that refuse to redeploy an existing version
- A digest is immutable by definition; an immutable tag makes the tag as trustworthy as the digest
- Pair with ==signing==: `cosign sign` attaches a signature to the digest, and the deploy side verifies it before pulling

### Software bill of materials (SBOM)
- A ==software bill of materials (SBOM)== is the ingredient list of an artifact
  - Every package inside it: name, version, supplier, license, and a package URL (`purl`) or CPE that scanners can match
- Two standard formats
  - ==SPDX== (Linux Foundation, ISO/IEC 5962): strong on licenses
  - ==CycloneDX== (OWASP): strong on security and dependency data
- Why it matters
  - A new CVE lands (think Log4Shell): search your SBOMs instead of opening every image
  - License review before shipping; US federal buyers ask for SBOMs (Executive Order 14028)
- `syft` (Anchore) reads an image, directory, or archive and writes either format

```console label="syft 1.54"
$ export SYFT_REGISTRY_INSECURE_USE_HTTP=true
$ syft scan -q "registry:$REG@$V1" -o table
NAME                    VERSION      TYPE
alpine-baselayout       3.6.5-r0     apk
alpine-keys             2.4-r1       apk
busybox                 1.36.1-r31   apk
ca-certificates-bundle  20260413-r0  apk
...
$ syft scan -q "registry:$REG@$V1" \
    -o spdx-json=sbom.spdx.json \
    -o cyclonedx-json=sbom.cdx.json
$ jq -r .spdxVersion sbom.spdx.json
SPDX-2.3
$ jq '.components[]
    | select(.name=="libssl3")
    | {name, version, type,
       license: .licenses[0].license.id}' \
    sbom.cdx.json
{
  "name": "libssl3",
  "version": "3.3.7-r0",
  "type": "library",
  "license": "Apache-2.0"
}
```

- `backup.sh` is not listed: an SBOM lists packages a tool can identify (apk, deb, rpm, pip, npm, Go modules, Java JARs), not loose scripts
- Scan by digest so the SBOM describes exactly the image you deploy
- Publish the SBOM with the artifact: `docker buildx build --sbom=true` attaches one to the image, and `grype sbom:sbom.cdx.json` checks it for known vulnerabilities

:::exam
- A tag can move; a digest cannot. A scenario where "the same version" behaves differently on two servers points to a re-pushed mutable tag; the fix is immutable tags or deploying by digest.
- 401 is an authentication problem (no or bad credentials); 403 is an authorization problem (valid user, missing permission).
- SPDX and CycloneDX are SBOM formats. An SBOM lists components and versions; it does not by itself say which ones are vulnerable; that takes a scanner.
:::
