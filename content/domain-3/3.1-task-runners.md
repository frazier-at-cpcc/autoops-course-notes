### What a task runner does
- A ==task runner== gives each repeatable job a short name
  - `make test`, `task lint`, `npm run build`, `invoke deploy`
  - Each task is a list of shell commands, plus its ==dependencies==: tasks that must run first
- Why automation teams use one
  - One command replaces ten copied from a wiki
  - The CI file stays short: it calls tasks instead of repeating their commands
  - Laptop and runner run the same steps, so "works on my machine" bugs show up locally
- Not a CI server: the pipeline decides when to run; the task runner decides what runs

| Runner | Task file | Run a task |
|---|---|---|
| GNU Make | `Makefile` | `make test` |
| Task (go-task) | `Taskfile.yml` | `task test` |
| npm scripts | `package.json` `"scripts"` | `npm run test` (or `npm test`) |
| Invoke (Python) | `tasks.py` with `@task` functions | `invoke test` |
| just | `justfile` | `just test` |

### Make
- The oldest runner, installed on almost every Linux image
- A ==target== names a task; its ==prerequisites== run first; its ==recipe== lines run in a shell
  - Recipe lines must start with a real tab; spaces give `missing separator`
  - `.PHONY` marks targets that are task names, not files to build
  - `@` at the start of a line hides the command echo
- Each recipe line is checked: a ==non-zero exit== stops make, and make itself exits `2`

```make label="Makefile"
COMPOSE := docker compose -f compose.test.yml
PSQL := $(COMPOSE) exec -T db psql -U ci -tA
.PHONY: lint test-env test clean

lint:
	yamllint -s inventory/

test-env:
	$(COMPOSE) up -d --wait

test: lint test-env
	@$(PSQL) -c "SELECT count(*) FROM devices" \
	  inventory | grep -qx 3
	@echo "inventory: 3 devices, tests passed"

clean:
	$(COMPOSE) down -v
```

- `make -n test` prints every command it would run, without running any of them

### Environment provisioning
- ==Environment provisioning==: create the services a test needs, just before the test
  - A database, a mock API, a DNS server, a containerized network OS image
- Throwaway and identical every run: built from files in the repository, seeded with known data, destroyed afterward
  - No shared "test database" that another job changed yesterday
- ==Docker Compose== is the usual tool for a few services

```yaml label="compose.test.yml"
services:
  db:
    image: postgres:17-alpine
    environment:
      POSTGRES_USER: ci
      POSTGRES_PASSWORD: throwaway-test-only
      POSTGRES_DB: inventory
    ports:
      - "127.0.0.1:18353:5432"
    volumes:
      - ./seed:/docker-entrypoint-initdb.d:ro
    healthcheck:
      # -h 127.0.0.1: TCP is up only after seeding
      test: pg_isready -h 127.0.0.1 -U ci
      interval: 2s
      retries: 15
```

- `up -d --wait` returns only when every service is ==healthy==
  - Without a health check, tests start while Postgres is still booting and fail at random
  - While it runs the `seed/` SQL, Postgres listens only on its local socket, so a TCP check waits for seeding
- The password guards a container that lives seconds; real credentials still come from a vault

```console label="Terminal"
$ make test
yamllint -s inventory/
docker compose -f compose.test.yml up -d --wait
 Container ao-f-inventory-db-1 Started
 Container ao-f-inventory-db-1 Waiting
 Container ao-f-inventory-db-1 Healthy
inventory: 3 devices, tests passed
$ make clean
docker compose -f compose.test.yml down -v
 Container ao-f-inventory-db-1 Removed
 Network ao-f-inventory_default Removed
```

- A second `make test` reuses the running container, so the laptop edit-test loop stays fast
- `down -v` also deletes the data volume; the next run starts from the seed

### One entry point, local and CI
- The pipeline calls the same ==entry point== a person would

```yaml label=".github/workflows/inventory.yml"
name: inventory
on: [push, pull_request]
jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v6
      - run: make test
      - if: always()   # tear down even on failure
        run: make clean
```

:::figure wide 3.1-task-entry-point.svg | `make test` runs lint, test-env, and test in order on any machine. `make clean` is a separate step; in CI, `if: always()` runs it even when a test failed.

- Moving to GitLab CI or Jenkins changes a few lines of YAML, not the test logic
- A failing task fails the step, because the ==exit code== passes straight through

```console label="Terminal"
$ make lint
yamllint -s inventory/
inventory/broken.yml
...duplication of key "ansible_host" in mapping...
make: *** [Makefile:6: lint] Error 1
$ echo $?
2
```

### Task and other runners
- ==Task (go-task)== reads YAML, runs on Linux, macOS, and Windows, and ships as one binary
  - `desc:` documents each task; `task --list` prints them
  - `deps:` run in parallel before the task; `sources:` and `generates:` skip work that is already up to date

```yaml label="Taskfile.yml"
version: '3'
vars:
  COMPOSE: docker compose -f compose.test.yml
tasks:
  test-env:
    desc: Start a throwaway Postgres
    cmds:
      - '{{.COMPOSE}} up -d --wait'
  test:
    desc: Lint, provision, and test
    deps: [test-env]
    cmds:
      - yamllint -s inventory/
      - >-
        {{.COMPOSE}} exec -T db psql -U ci -tA
        -c "SELECT count(*) FROM devices"
        inventory | grep -qx 3
  clean:
    desc: Remove the test environment
    cmds:
      - '{{.COMPOSE}} down -v'
```

```console label="task 3.54"
$ task --list
task: Available tasks for this project:
* clean:          Remove the test environment
* test:           Lint, provision, and test
* test-env:       Start a throwaway Postgres
```

- ==npm scripts== live in `package.json`; `pretest` and `posttest` scripts run automatically around `test`
- ==Invoke== suits Python teams: tasks are decorated functions, so they can loop over inventory or call libraries before running commands with `c.run()`

:::exam
- A task runner (make, Task, npm scripts, Invoke) defines named, repeatable steps. A scenario where CI and developers run tests differently is solved by one task entry point both of them call.
- Environment provisioning creates the services a test needs (often `docker compose up`) before the tests and removes them after. Watch for answers that share one long-lived test environment between jobs.
- A cleanup step must run even after a failure: `if: always()` in GitHub Actions, `after_script` in GitLab CI, `post { always { } }` in Jenkins.
:::
