### Pipeline as code
- ==Pipeline as code==: a ==pipeline definition== is a file in the repository that describes the whole pipeline
  - Versioned with the code it builds; changed through a pull request; rolled back with `git revert`
  - The CI system reads the file from the commit being built, so each branch can carry its own pipeline changes
- Three formats to read on the exam: a `Jenkinsfile` (Groovy-based DSL), `.gitlab-ci.yml` (YAML), and a GitHub Actions workflow (YAML in `.github/workflows/`)
- Below, the same pipeline in each format
  - Build: render a switch config into `dist/`
  - Test: check the rendered file
  - Deploy: only on `main`; Release: only for a tag
  - A 10-minute time limit on every format

### Jenkinsfile
- ==Declarative pipeline==: a fixed structure inside `pipeline { }`, checked before it runs
- ==Scripted pipeline==: plain Groovy inside `node { }`; flexible, but errors appear only at run time

```groovy label="Jenkinsfile"
pipeline {
  agent any
  options { timeout(time: 10, unit: 'MINUTES') }
  stages {
    stage('Build') {
      steps {
        sh 'mkdir -p dist'
        sh 'echo "vlan 10" > dist/core-sw1.cfg'
      }
    }
    stage('Test') {
      steps {
        sh 'grep -q "vlan 10" dist/core-sw1.cfg'
      }
    }
    stage('Deploy') {
      when { branch 'main' }
      steps {
        sh 'echo "deploy $GIT_COMMIT"'
      }
    }
    stage('Release') {
      when { buildingTag() }
      steps {
        sh 'echo "release $TAG_NAME"'
      }
    }
  }
  post {
    failure { echo 'notify #netops' }
  }
}
```

- Anatomy
  - `agent`: where it runs (`any`, a `label`, or a `docker` image)
  - `stages` / `stage` / `steps`: the work, in order; stages share one workspace, so `dist/` is still there for Test
  - `when`: the condition for a stage; `options`: timeout, retry, build retention
  - `post`: `always`, `success`, `failure` blocks after the run; also `environment`, `parameters`, `triggers`
- A ==multibranch pipeline== job finds every branch and tag with a `Jenkinsfile` and sets `BRANCH_NAME`, `TAG_NAME`, and `CHANGE_ID`
- Validate before committing with the declarative linter (also `jenkins-cli declarative-linter`)

```console label="Terminal"
$ J=http://127.0.0.1:18410
$ curl -s -X POST -F "jenkinsfile=<Jenkinsfile" \
    $J/pipeline-model-converter/validate
Jenkinsfile successfully validated.
```

- Leave the `steps { }` wrapper out of the Test stage and the same call fails with: Expected one of "steps", "stages", or "parallel" for stage "Test"
- The multibranch run for `main`, trimmed to the last two stages

```console label="Jenkins console, netops/main"
[Pipeline] { (Deploy)
deploy 9a2956fa7d0012ddb1bb04952d79bfe2ac36f42d
[Pipeline] { (Release)
Stage "Release" skipped due to when conditional
Finished: SUCCESS
```

### .gitlab-ci.yml
- One file at the repository root; every top-level key that is not a reserved ==keyword== is a ==job==

```yaml label=".gitlab-ci.yml"
stages: [build, test, deploy]

default:
  image: alpine:3.20
  timeout: 10m

build:
  stage: build
  script:
    - mkdir -p dist
    - echo "vlan 10" > dist/core-sw1.cfg
  artifacts:
    paths: [dist/]

test:
  stage: test
  script:
    - grep -q "vlan 10" dist/core-sw1.cfg

deploy:
  stage: deploy
  rules:
    - if: $CI_COMMIT_BRANCH == "main"
  script:
    - echo "deploy $CI_COMMIT_SHA"

release:
  stage: deploy
  rules:
    - if: $CI_COMMIT_TAG
  script:
    - echo "release $CI_COMMIT_TAG"
```

- Anatomy
  - `stages`: the order; `default`: settings every job inherits
  - Each job: `stage`, `script` (required except in trigger jobs), `image`, `rules`, `needs`, `variables`
  - `artifacts`: files handed to later jobs; each job starts in a fresh container, so without this `test` has no `dist/`
  - `include:` pulls in shared templates from other files or projects
- Validate with the pipeline editor or CI Lint in GitLab; run locally with `gitlab-ci-local`
  - `--force-shell-executor` runs each job in your shell instead of pulling its `image`; `--shell-isolation` gives each job its own copy, so artifacts really move

```console label="Terminal"
$ gitlab-ci-local --force-shell-executor \
    --shell-isolation
build   exported artifacts in 118 ms
test    imported artifacts in 80 ms
deploy  imported artifacts in 87 ms
deploy  > deploy e897e39de70c708577d13b96b5bb20e38dbfc169
 PASS  build
 PASS  test
 PASS  deploy
```

### GitHub Actions workflow
- Any number of YAML files in `.github/workflows/`; the objectives call this one `github-actions.yml`
- A ==workflow== file: `on:` lists the triggers; `jobs:` run in parallel unless `needs:` orders them

```yaml label=".github/workflows/github-actions.yml"
name: netops-ci
on:
  push:
    branches: [main]
    tags: ['v*']
  pull_request:

jobs:
  build:
    runs-on: ubuntu-latest
    timeout-minutes: 10
    steps:
      - uses: actions/checkout@v7
      - name: Build
        run: |
          mkdir -p dist
          echo "vlan 10" > dist/core-sw1.cfg
      - name: Test
        run: grep -q "vlan 10" dist/core-sw1.cfg

  deploy:
    needs: build
    if: github.ref == 'refs/heads/main'
    runs-on: ubuntu-latest
    steps:
      - run: echo "deploy $GITHUB_SHA"

  release:
    needs: build
    if: github.ref_type == 'tag'
    runs-on: ubuntu-latest
    steps:
      - run: echo "release $GITHUB_REF_NAME"
```

- Anatomy
  - `runs-on`: the runner label; `steps`: either `uses:` (a reusable ==action==) or `run:` (shell)
  - Build and Test are steps in one job, so they share a workspace; separate jobs would need `actions/upload-artifact` and `download-artifact`
  - Pass event data through environment variables (`$GITHUB_REF_NAME`) rather than pasting `${{ }}` expressions into scripts; a branch name is user input
  - `permissions:` limits what the job's `GITHUB_TOKEN` can do
- Validate with `actionlint`; run locally with `act` (it maps `ubuntu-latest` to a Docker image)

```console label="Terminal"
$ actionlint && echo "actionlint: no problems"
actionlint: no problems
$ act push -e tag.json --json > run.json
$ jq -r 'select(.jobResult)
    | "\(.jobID) \(.jobResult)"' run.json
build success
release success
```

:::wide
| | Jenkinsfile | .gitlab-ci.yml | GitHub Actions |
|---|---|---|---|
| Language | Groovy-based DSL | YAML | YAML |
| Location | repository root (any path in job config) | repository root | `.github/workflows/*.yml` |
| Unit of work | `stage` with `steps` | job (top-level key) | job with `steps` |
| Ordering | stages in sequence; `parallel` block | `stages` plus `needs` | parallel unless `needs` |
| Condition | `when { branch 'main' }` | `rules: - if:` | `if:` expression |
| Files between steps | shared workspace | `artifacts` | upload / download artifact actions |
| Runs on | `agent` | runner, `image`, `tags` | `runs-on`, `container` |
| After failure | `post { failure { } }` | `when: on_failure` | `if: failure()` |
| Check it locally | declarative linter | CI Lint, `gitlab-ci-local` | `actionlint`, `act` |
:::

:::exam
- Identify the platform from the file: `pipeline { agent ... stages { stage(...) { steps ... } } }` is a declarative Jenkinsfile; top-level job names with `script:` and `stages:` is `.gitlab-ci.yml`; `on:`, `jobs:`, `runs-on:`, and `steps:` with `uses:` / `run:` is a GitHub Actions workflow.
- Scenario questions often hinge on one line: a job that skips on a tag (`if: $CI_COMMIT_BRANCH == "main"`), a missing `artifacts` entry so the next job cannot find the file, or `needs` that forces an order.
- A declarative Jenkinsfile must have `agent` and `stages`, and every `stage` needs `steps` (or nested `stages` / `parallel`).
:::
