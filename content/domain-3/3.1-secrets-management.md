### Secrets in the pipeline
- A ==secret== is any value that grants access
  - API tokens, database passwords, SSH and TLS private keys, cloud access keys, SNMP community strings
- ==Secret sprawl==: one password pasted into CI variables, `.env` files, playbook vars, and a wiki page
  - Nobody knows every copy, so nobody can rotate it safely
- CI platforms ==mask secrets== in job logs
  - GitHub Actions prints registered secrets as `***`; `::add-mask::VALUE` masks a value created during the run
  - GitLab: masked variables are hidden in logs; protected variables reach only protected branches and tags
  - Masking is cosmetic: a step can still base64 the value or send it over the network

### Encrypted key vaults
- An ==encrypted key vault== stores secrets encrypted at rest and releases them only to authenticated callers that a ==policy== allows
  - Every read is in the audit log: "who read the switch password last Tuesday?"

| Vault | Notes |
|---|---|
| HashiCorp Vault | self-hosted or HCP; KV, dynamic secrets, PKI |
| AWS Secrets Manager | KMS-encrypted; rotation by Lambda or managed rotation |
| Azure Key Vault | secrets, keys, certificates; RBAC; soft delete |
| Google Secret Manager | versioned; rotation reminders via Pub/Sub |

- A dev server (`vault server -dev`) is unsealed and in-memory: lab only

```console label="Vault 2.2 dev server"
$ vault kv put -mount=secret ci/netbox \
    api_token=nb-7f3a9c
==== Secret Path ====
secret/data/ci/netbox
...
version            1
$ vault kv get -mount=secret -field=api_token \
    ci/netbox
nb-7f3a9c
```

### Tokens, leases, and expiration
- Every Vault login returns a ==token== with a ==TTL== (time to live) and a policy

```hcl label="ci-read policy"
path "secret/data/ci/*" {
  capabilities = ["read"]
}
```

```console label="Terminal"
$ vault token create -policy=ci-read -ttl=15s
Key                  Value
---                  -----
token                hvs.CAESIFZ-NewiH1dhcsq4...
token_duration       15s
token_policies       ["ci-read" "default"]
$ export VAULT_TOKEN=$CI_TOKEN   # 15s later
$ vault kv get -mount=secret ci/netbox
Code: 403. Errors:
* 2 errors occurred:
	* permission denied
	* invalid token
```

- While it was valid, the same token could read but got `permission denied` on a write
- ==Lease management and expiration==
  - A ==lease== is Vault's record of a secret it handed out: ID, duration, renewable or not
  - Renewing extends a lease but never past the role's ==max_ttl==; Vault caps the request and warns
  - When a lease expires, Vault deletes the secret itself
- Size the TTL to the job: a 10-minute pipeline needs a credential for 10 minutes, not 90 days

### Dynamic secrets and revocation
- A ==dynamic secret== is created on demand, unique to one caller, and destroyed when its lease ends
  - Vault's database engine runs `CREATE ROLE` in Postgres for each request; this `ci` role has `default_ttl=2m` and `max_ttl=10m`
  - The read also returns a `lease_id` (trimmed below); save it

```console label="Terminal"
$ vault read db/creds/ci
lease_duration     2m
lease_renewable    true
password           rmnxoE6-NQf3ew1dX42T
username           ci-qr7cxiir
$ LEASE=db/creds/ci/B2tPcO50C5LKh93jJMLDW6KJ
$ vault lease lookup $LEASE
expire_time     2026-10-19T12:57:53.343306968Z
ttl             1m58s
$ vault lease renew -increment=5m $LEASE
lease_duration     5m
$ vault lease revoke $LEASE
All revocation operations queued successfully!
```

- ==Revocation== ends a secret before its TTL; here `ci-qr7cxiir` vanished from Postgres
  - Every credential a role issued: `vault lease revoke -prefix db/creds/ci` (the breach button)
  - `vault token revoke` also revokes the token's children and their leases

:::figure wide 3.1-secret-lease.svg | A dynamic database secret. The database user exists only while its lease is alive; revoking the lease, or letting it expire, makes Vault drop the user.

- ==Dynamic secret rotation==: credentials change so often that a leaked one soon stops working
  - Dynamic secrets rotate by design; static ones need a ==rotation schedule== (Secrets Manager rotation, Key Vault expiry dates, Vault static roles)
  - `vault write -f db/rotate-root/inventory` gave the Postgres admin a password only Vault knows; the old one stopped working

| | Static secret | Dynamic secret |
|---|---|---|
| Created | once, by a person | per request, by the vault |
| Shared | by every job | unique to one job |
| Lifetime | until someone rotates it | the lease TTL |
| After a leak | find and rotate everywhere | revoke the lease |

### Tokenization
- ==Tokenization== swaps a sensitive value for a random stand-in (a token) with no mathematical link to the original
  - The original stays in a protected token vault; only authorized systems can ==detokenize==
  - Encryption differs: anyone holding the key can reverse ciphertext
- Lets pipelines use realistic data without real data
  - Test fixtures carry tokenized card numbers, so CI logs and test databases never hold real ones; fewer systems in PCI DSS scope
- Offered by Vault Enterprise (Transform engine), payment providers, and cloud DLP services
  - Not the same as a Vault or API token: those are credentials, not stand-ins for data

### Zero Trust for pipelines
- ==Zero Trust== (NIST SP 800-207): no trust based on network location; verify every request, least privilege, assume breach
- Applied to CI
  - No long-lived cloud keys stored in CI variables
  - The job proves its identity with a short-lived ==OIDC== token; Vault checks the repository and branch claims before issuing anything
  - Per-job, short-TTL credentials on ephemeral runners; everything logged and revocable

```yaml label=".github/workflows/deploy-acl.yml"
name: deploy-acl
on: push
jobs:
  deploy:
    runs-on: ubuntu-latest
    permissions:
      id-token: write   # request an OIDC token
      contents: read
    steps:
      - uses: actions/checkout@v6
      - uses: hashicorp/vault-action@v3
        with:
          url: https://vault.example.net
          method: jwt
          role: netops-deploy
          secrets: |
            secret/data/ci/netbox api_token | TOKEN
      - run: ./push-acl.sh  # TOKEN shows as ***
```

- No secret is stored in the repository or CI settings; `vault-action` masks each value it fetches

:::exam
- Match the term to the behavior: a lease that the vault cleans up at its TTL is lease management and expiration; ending it early is revocation; a credential created per job is a dynamic secret.
- Masked CI variables hide values in logs but do not stop a malicious step from stealing them. Removing stored credentials from CI points to OIDC federation with a vault (Zero Trust).
- Tokenization replaces data with a meaningless stand-in and keeps the original in a vault; encryption transforms data with a key. A distractor will treat them as the same.
:::
