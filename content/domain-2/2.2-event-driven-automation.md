### From polling to events
- Polling: a cron job asks "anything new?" every five minutes
  - Wasted runs when nothing changed; up to five minutes late when something did
- Event-driven: the system that changed announces it, and automation reacts in seconds
  - An ==event== is a record that something happened: type, source, time, data
- ==Cloud-based events== come in three building blocks: notifications, queues, and functions

:::figure wide 2.2-event-flow.svg | A topic pushes a copy of each event to every subscriber. A queue holds work until one consumer finishes it; repeated failures move the message to a dead-letter queue.

### Notification-based events
- ==Notification-based events== push a message to whoever is subscribed at that moment
  - ==Publish/subscribe (pub/sub)==: one publisher, many subscribers, each gets its own copy
  - The publisher does not know or wait for the subscribers
- Examples: webhooks (GitHub POSTs to the CI server on every push), AWS SNS and EventBridge, Azure Event Grid, S3 "object created" events
- No subscriber, no delivery: a topic is not storage
  - Below, the first event fires before the `audit` and `backup` queues subscribe, and it is simply dropped

```console label="Terminal"
$ python3 events.py
notify: dropped, nobody subscribed
notify: delivered
  audit received core-sw1 v43
  backup received core-sw1 v43
```

### Messaging queues
- A ==messaging queue== stores each message until one consumer handles it
  - Point-to-point: each message is processed once, by one worker
  - Producers and consumers run at their own speed; the queue absorbs bursts
- ==Competing consumers==: add workers to drain the queue faster
- The consumer ==acknowledges== (acks) a message only after the work succeeds
  - No ack (crash, timeout) and the broker hands the message out again
  - SQS hides an in-flight message for its visibility timeout (30 seconds by default)
- Examples: AWS SQS, RabbitMQ, Azure Service Bus, Redis streams
- ==Fan-out==: subscribe several queues to one topic (SNS to SQS) for a durable copy per team

:::wide
| | Pub/sub topic | Queue |
|---|---|---|
| Who gets a message | Every current subscriber | Exactly one consumer |
| Stored until handled | No | Yes, until acked or it expires |
| Typical use | Tell many systems something happened | Hand a unit of work to a pool of workers |
| Cloud examples | SNS, EventBridge, Event Grid | SQS, Service Bus, Storage Queues |
:::

### At-least-once delivery and dead letters
- Most queues promise ==at-least-once delivery==
  - Never lost once accepted, but it can arrive twice (the worker finished, then crashed before the ack)
  - At-most-once can lose messages; exactly-once holds only within limits, such as SQS FIFO deduplication over five minutes
- So every consumer must be an ==idempotent consumer==
  - Record each message ID (Redis, a unique database key) and skip ones already done
  - Or make the action safe to repeat: upsert instead of insert
- A ==dead-letter queue (DLQ)== catches a message that keeps failing
  - After N deliveries (SQS `maxReceiveCount`, RabbitMQ `x-delivery-limit`) it moves aside, so one poison message cannot block the queue
  - Alert on DLQ depth; a human fixes and replays, or discards

```python label="events.py (excerpt)"
DLQ = "jobs.backup.dlq"
args = {
    "x-queue-type": "quorum",
    "x-delivery-limit": 2,
    "x-dead-letter-exchange": "",
    "x-dead-letter-routing-key": DLQ,
}
ch.queue_declare(DLQ, durable=True)
ch.queue_declare("jobs.backup", durable=True,
                 arguments=args)


def handle(m, p, body):
    mid = p.message_id
    if mid in seen:
        return f"{mid}: duplicate, skipped"
    seen.add(mid)
    return f"{mid}: backed up {body.decode()}"
```

### Function as a service (FaaS)
- ==Function as a service (FaaS)==: upload a function; the platform runs it when an event arrives
  - No server to patch; scales out per event and down to zero; billed per request and millisecond
- Triggers: HTTP request, queue message, topic, schedule, file upload, database change
- Platforms: AWS Lambda, Azure Functions, Google Cloud Run functions; self-hosted OpenFaaS or Knative
- Short and stateless by design
  - Lambda stops at 15 minutes; nothing local survives between calls; the first call pays a ==cold start==
- Automation uses: tag new VMs, close a security group opened to `0.0.0.0/0`, back up a switch when its config changes

```python label="handler.py (excerpt)"
def handler(event, context):
    """Called once per batch of queue messages."""
    failed = []
    for record in event["Records"]:
        job = json.loads(record["body"])
        try:
            backup(job["host"])
        except ValueError:
            failed.append(record["messageId"])
    # Only the failed messages go back to the queue
    return {"batchItemFailures": [
        {"itemIdentifier": i} for i in failed]}
```

```console label="Terminal"
$ python3 invoke.py event.json
{"batchItemFailures": [{"itemIdentifier": "m-2"}]}
```

- `invoke.py` feeds the handler a two-message, SQS-shaped batch; no cloud account is involved
- With an SQS trigger and `ReportBatchItemFailures` on, Lambda returns only `m-2` to the queue; without it, the whole batch is retried

:::exam
- "Every subscribed system must be told" is pub/sub (SNS, Event Grid, webhooks). "Each job must be processed once, even if workers are offline for an hour" is a queue (SQS, Service Bus).
- At-least-once delivery means duplicates are possible, so the answer is an idempotent consumer. Messages that fail again and again go to a dead-letter queue.
- FaaS is event-triggered, short-running, and stateless; a two-hour batch job is the distractor that does not fit.
:::
