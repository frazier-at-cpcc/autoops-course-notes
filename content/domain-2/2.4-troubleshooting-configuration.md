### Work the layers in order
- An API call, an agent check-in, and a playbook task that calls a controller all fail in the same places
- Read the exact error first; the ==curl exit code== or HTTP status usually names the layer
  - `curl -v` shows how far the call got: resolved, connected, TLS done, request sent
- Fix the lowest broken layer first
  - A TLS error means DNS and TCP already worked; an HTTP `401` means TLS already worked

:::figure wide 2.4-failure-ladder.svg | Each layer depends on the one to its left. The curl exit code or HTTP status tells you which layer stopped the call.

### API communication failures
- Four ==API communication failures==: a DNS miss, ==connection refused==, a ==timeout==, and a ==proxy== that wants credentials (curl exit codes in parentheses)

:::wide
```console label="Terminal"
$ curl -sS http://inv.lab.invalid:18300/
curl: (6) Could not resolve host: inv.lab.invalid
$ getent hosts inv.lab.invalid; echo "exit=$?"
exit=2
$ curl -sS http://127.0.0.1:18319/
curl: (7) Failed to connect to 127.0.0.1 port 18319 after 0 ms: Couldn't connect to server
$ curl -sS -m 3 http://127.0.0.1:18318/
curl: (28) Operation timed out after 3002 milliseconds with 0 bytes received
$ https_proxy=http://127.0.0.1:18317 curl -sS https://api.example.com/
curl: (56) CONNECT tunnel failed, response 407
```
:::

:::wide
| Symptom | Likely cause | Check or fix |
|---|---|---|
| Could not resolve host | Typo in the hostname, missing DNS record, wrong resolver | `getent hosts`, `dig`; fix the record or the URL in the config |
| Connection refused | Host is up, nothing listens on that port: service down, wrong port, bound to 127.0.0.1 only | `ss -tlnp` and `systemctl status` on the server |
| Timeout | Firewall or security group dropping packets, bad route, or a hung application | `nc -zv host port`; firewall rules; set `--connect-timeout` and `-m` in scripts |
| `407`, CONNECT tunnel failed | The proxy wants credentials, or an internal host is being sent through the proxy | `https_proxy`, `no_proxy`; `curl -v` shows the CONNECT |
| `401`, `403`, `429` | Bad or expired token; missing permission; rate limit (objective 2.3) | `curl -i`; read `WWW-Authenticate` and `Retry-After`; only `429` improves by waiting |
:::

### Agent communication issues
- ==Agent==-based tools run a daemon on every managed node that talks to a central server
  - Zabbix: server polls the agent on 10050; the agent sends active checks to the server on 10051
  - Puppet agent to Puppet Server on 8140; Salt minion to master on 4505 and 4506
  - Ansible is agentless (SSH, WinRM), so its "agent" problems are SSH or WinRM problems
- Two Zabbix agent 2 containers: one with a server name that does not resolve, one whose server is not listening

:::wide
```console label="Terminal"
$ docker logs ao-e-zbx 2>&1 | grep -m2 -E "cannot connect|started to fail"
2026/10/19 13:00:50.004532 [101] cannot connect to [zbx.lab.invalid:10051]: dial tcp: lookup zbx.lab.invalid on 8.8.8.8:53: no such host
2026/10/19 13:00:50.004543 [101] active check configuration update from host [edge-sw-mon] started to fail
$ docker logs ao-e-zbx2 2>&1 | grep -m1 "cannot connect"
2026/10/19 13:00:50.002120 [101] cannot connect to [127.0.0.1:10051]: dial tcp :0->127.0.0.1:10051: connect: connection refused
```
:::

- The agent keeps running and the server shows the host as unavailable; only the agent's log has the cause
- Checklist
  - Server address and port in the agent config: `ServerActive=` in `zabbix_agent2.conf`, `server =` in `puppet.conf`
  - DNS and firewall rules as seen from the agent, in the direction the connection flows
  - Agent hostname matches the host defined on the server
  - Certificates or PSK match (Puppet agents need a certificate signed by the server's CA); NTP running, since clock skew breaks certificates
  - Restart the agent after editing its config

### Application failures
- A unit that crashes on start: systemd restarts it, then gives up

:::wide
```console label="Terminal"
$ systemctl status invsync --no-pager
× invsync.service - Inventory sync agent
     Loaded: loaded (/etc/systemd/system/invsync.service; enabled; preset: enabled)
     Active: failed (Result: exit-code) since Mon 2026-10-19 13:01:01 UTC; 1s ago
    Process: 193 ExecStart=/usr/bin/python3 /opt/invsync/agent.py (code=exited, status=1/FAILURE)
$ journalctl -u invsync -o cat --no-pager | grep -E "Error|repeated" | tail -2
json.decoder.JSONDecodeError: Expecting property name enclosed in double quotes: line 4 column 1 (char 62)
invsync.service: Start request repeated too quickly.
$ systemctl show invsync -p NRestarts -p ExecMainStatus
NRestarts=5
ExecMainStatus=1
```
:::

- The cause was a trailing comma in `/etc/invsync/agent.json` (next topic)
- ==Start request repeated too quickly==: by default, five failed starts within 10 seconds stops the restarts
  - After the fix: `systemctl reset-failed invsync`, then `systemctl restart invsync`
  - After editing the unit file itself: `systemctl daemon-reload`
- ==journalctl== flags: `-u unit`, `-n 50` last lines, `-f` follow, `-b` this boot, `--since "10 min ago"`, `-p err` errors only
- Active is not the same as working: with valid JSON the service ran, and its log showed the next layer down

```console label="Terminal"
$ systemctl is-active invsync
active
$ journalctl -u invsync -n 1 --no-pager -o cat
cannot reach http://inv.lab.invalid:8080: <urlopen error [Errno -2] Name or service not known>
```

- Containers: the ==exit code== and the logs survive after the container stops

:::wide
```console label="Terminal"
$ docker ps -a --filter name=ao-e-web --format "{{.Names}}: {{.Status}}"
ao-e-web: Exited (1) Less than a second ago
$ docker logs ao-e-web 2>&1 | tail -1
nginx: [emerg] unknown directive "proxy_pas" in /etc/nginx/conf.d/default.conf:4
$ docker run --rm alpine:3.20 inventory-sync 2>&1 | grep -o "exec:.*"
exec: "inventory-sync": executable file not found in $PATH
$ docker run --rm alpine:3.20 inventory-sync 2>/dev/null; echo "exit=$?"
exit=127
$ docker inspect -f "{{.State.ExitCode}} OOMKilled={{.State.OOMKilled}}" ao-e-kill
137 OOMKilled=false
```
:::

- Exit codes to know: `1` general error, `126` found but not executable, `127` command not found, `137` = 128 + 9 (SIGKILL: OOM killer or `docker kill`), `143` = 128 + 15 (SIGTERM)
- Test a config before you load it: `nginx -t`, `apachectl configtest`, `sshd -t`, `named-checkconf`; the nginx typo above fails `nginx -t` without taking the site down
- `5XX` from a reverse proxy: the proxy is fine, the backend is not

```console label="Terminal"
$ P=http://127.0.0.1:18310
$ curl -s -o /dev/null -w "%{http_code}\n" $P/down/
502
$ curl -s -o /dev/null -w "%{http_code}\n" $P/slow/
504
```

- nginx's error log names the cause: `connect() failed (111: Connection refused)` for the `502`, `upstream timed out (110: Operation timed out)` for the `504`

### Certificate issues
- Four local `openssl s_server` instances show the common ==certificate issues==; `root.pem` is the lab root CA
  - 18320 is correct (leaf plus intermediate), 18321 sends only the leaf, 18322 is expired, 18323 is self-signed
  - The first curl below does not pass `--cacert`, so the lab CA is untrusted
- Read the certificate first, then let curl and `openssl s_client` try the servers

:::wide
```console label="Terminal"
$ openssl x509 -in api.pem -noout -subject -issuer -enddate -ext subjectAltName
subject=CN = api.lab.test
issuer=CN = Lab Issuing CA
notAfter=Jan 17 13:01:14 2027 GMT
X509v3 Subject Alternative Name:
    DNS:api.lab.test, IP Address:127.0.0.1
$ curl -sS https://127.0.0.1:18320/
curl: (60) SSL certificate problem: unable to get local issuer certificate
$ curl -sS https://127.0.0.1:18323/
curl: (60) SSL certificate problem: self-signed certificate
$ curl -sS --cacert root.pem https://localhost:18320/
curl: (60) SSL: no alternative certificate subject name matches target host name 'localhost'
$ curl -sS --cacert root.pem https://127.0.0.1:18322/
curl: (60) SSL certificate problem: certificate has expired
$ curl -sS --cacert root.pem https://127.0.0.1:18321/
curl: (60) SSL certificate problem: unable to get local issuer certificate
$ openssl s_client -connect 127.0.0.1:18321 -CAfile root.pem -brief </dev/null 2>&1 | grep -E "depth|error"
depth=0 CN = api.lab.test
verify error:num=20:unable to get local issuer certificate
verify error:num=21:unable to verify the first certificate
$ openssl s_client -connect 127.0.0.1:18320 -CAfile root.pem -showcerts </dev/null 2>/dev/null | grep -E "^ [0-9] s:|^Verify return"
 0 s:CN = api.lab.test
 1 s:CN = Lab Issuing CA
Verify return code: 0 (ok)
```
:::

- Port 18321 is the ==incomplete chain== trap: curl says "unable to get local issuer" even with the right CA, because the server sent only its own certificate
  - `s_client` adds error 21, and a healthy server lists two certificates (leaf, then intermediate)

:::wide
| Problem | What the client reports | Fix |
|---|---|---|
| Expired | `certificate has expired` (OpenSSL error 10) | Renew; automate renewal (ACME, cert-manager); monitor with `openssl x509 -checkend` |
| Hostname mismatch | `no alternative certificate subject name matches target host name` | Use a name listed in the SAN, or reissue with the right SAN (clients ignore the CN) |
| Untrusted CA | `unable to get local issuer certificate` (20), `self-signed certificate` (18) | Add the CA to the client's trust store: `--cacert`, `update-ca-certificates`, `REQUESTS_CA_BUNDLE` |
| Incomplete chain | curl: error 20; `s_client`: error 21 `unable to verify the first certificate` | Configure the server with the full chain: leaf plus intermediates |
| Wrong clock | `certificate is not yet valid` (9), or a false expiry | Fix NTP on the client |
:::

- Never fix a certificate error with `curl -k`, `verify=False`, or `validate_certs: false` in automation; it removes the protection TLS exists for

:::exam
- Map the message to the layer: "could not resolve" is DNS, "connection refused" is a port with no listener, a timeout is usually a firewall, `curl: (60)` is a certificate, `401`/`403` is credentials or permissions.
- An agent that is running but whose host shows as unavailable is a communication problem: check the server address in the agent config, DNS, and the firewall in the direction the agent connects.
- Same "unable to get local issuer certificate" error, two causes: the client does not trust the CA (fix the client trust store) or the server did not send its intermediate (fix the server chain).
:::
