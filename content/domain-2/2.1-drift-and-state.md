### Desired state and drift
- Configuration management tools describe the ==desired state==: what the switch, server, or cloud network should look like
  - The tool compares that description to the ==current state== and changes only what differs
- ==Drift== is any gap between the code and what is really running
  - An engineer fixes an outage by hand at 2 a.m. and never updates the repo
  - A console click, a vendor support session, a script outside the pipeline
  - A failed or half-finished apply
- Drift means the code is no longer the truth
  - The next apply silently undoes the hand fix, and a rebuild from code no longer matches production
- ==Drift detection and remediation== is the loop: compare often, report the gap, then put code and reality back in agreement

### Terraform state
- Terraform keeps a ==state file== (`terraform.tfstate`): a JSON map from each resource address in the code to the real object it created
  - `aws_vpc.lab` in code maps to `vpc-0a1b2c...` in AWS
  - Records every attribute Terraform knows, plus dependencies and outputs
- State is how Terraform knows what it owns
  - Without it, Terraform would try to create everything again
  - `terraform state list` and `terraform state show <address>` read it; never hand-edit the JSON

```console label="Terminal"
$ terraform state list
local_file.motd
$ jq '{version, serial, lineage}' terraform.tfstate
{
  "version": 4,
  "serial": 1,
  "lineage": "9023d652-1ee4-6b76-e92d-3c3d40c3c323"
}
```

- `serial` goes up on every write; `lineage` identifies this state's history, so Terraform refuses to overwrite it with an unrelated state
- State holds ==secrets in plain text==: database passwords, private keys generated by the `tls` provider
  - Never commit it: add `*.tfstate` and `*.tfstate.*` to `.gitignore`
  - Store it encrypted, with access limited to the pipeline and a few admins

### Remote backends and locking
- A ==backend== decides where state lives
  - Default `local` backend: a file on one laptop; fine for a lab, wrong for a team
  - ==Remote backends==: Amazon S3, Azure Blob Storage (`azurerm`), Google Cloud Storage (`gcs`), HCP Terraform, Consul, PostgreSQL (`pg`)
- A remote backend gives one shared copy, encryption at rest, versioning for rollback, and access control
- ==State locking== stops two runs from writing at once
  - The first `plan` or `apply` takes the lock; anyone else waits or fails
  - S3: `use_lockfile = true` writes a `.tflock` object beside the state (Terraform 1.10 and later)
  - The older DynamoDB lock table (`dynamodb_table`) is deprecated

```hcl label="backend.tf"
terraform {
  backend "s3" {
    bucket       = "netops-tfstate"
    key          = "core/motd.tfstate"
    region       = "us-east-1"
    encrypt      = true
    use_lockfile = true
  }
}
```

- Settings that differ per environment can stay out of the file: `terraform init -backend-config=...` (partial configuration)
- While one apply runs, a second engineer's plan is refused

```console label="Second engineer, during an apply"
$ terraform plan
Error: Error acquiring the state lock
Lock Info:
  Path:      netops-tfstate/core/motd.tfstate
  Operation: OperationTypeApply
  Who:       root@vm
```

- Wait for the other run; never reach for `-lock=false`
- A crashed run can leave a stale lock: confirm nobody is running, then `terraform force-unlock <LOCK_ID>`

### Detecting drift
- `terraform plan` refreshes state from the real infrastructure, then compares it to the code
- ==Detailed exit codes==: `-detailed-exitcode` turns the answer into something a pipeline can act on
  - `0`: no changes; `2`: changes pending (drift or new code); `1`: error

:::figure wide 2.1-drift-loop.svg | Plan reads the real infrastructure, compares it to the code through state, and reports with an exit code. Each remediation moves a different side.

- Real drift: someone edits a file that Terraform manages

```console label="Terminal"
$ echo "Free Wi-Fi password: guest123" > motd.txt
$ terraform plan -detailed-exitcode
  # local_file.motd will be created
Plan: 1 to add, 0 to change, 0 to destroy.
$ echo $?
2
```

- The `local` provider treats changed content as a missing file, so the fix shows as a create; a cloud provider would usually show `~ update in-place`
- Schedule it: a nightly pipeline job runs the plan and alerts (or opens a ticket) on exit code 2
  - Some platforms do this for you: HCP Terraform health assessments, Spacelift, env0

### Remediating drift
- First decide which side is right: the code or the change someone made

:::wide
| Situation | Remediation | Command |
|---|---|---|
| The hand change was wrong | Re-apply the code; it overwrites the drift | `terraform apply` |
| The change was right | Copy it into the code, review, then apply (plan shows no changes) | edit `.tf`, `terraform apply` |
| Accept reality into state without changing anything | Refresh-only run updates state to match the real objects | `terraform apply -refresh-only` |
| Someone built a resource outside Terraform | Bring it under management | `import` block, or `terraform import` |
| Terraform should stop managing a resource | Remove it from state and leave it running | `removed` block, or `terraform state rm` |
:::

- `terraform plan -refresh-only` lists "Objects have changed outside of Terraform" and proposes no fixes
  - Replaces the deprecated `terraform refresh`, which updated state without review
- `import` blocks (Terraform 1.5 and later) put imports in code review; `terraform plan -generate-config-out=generated.tf` writes a starting configuration
- Prevent repeat drift: remove console write access, make the pipeline the only path to production

### Configuration drift with Ansible
- Ansible has no state file; it checks the target every run and acts only if the target differs (idempotent modules)
- `--check` is a dry run: report what would change, change nothing
- `--diff` shows the exact lines; together they are a drift report

```yaml label="ntp.yml"
- name: Enforce the NTP baseline
  hosts: localhost
  connection: local
  gather_facts: false
  tasks:
    - name: Chrony points at the site NTP servers
      ansible.builtin.copy:
        dest: chrony.conf
        mode: "0644"
        content: |
          server 10.0.0.1 iburst
          server 10.0.0.2 iburst
          makestep 1.0 3
```

```console label="After a hand edit"
$ ansible-playbook ntp.yml --check --diff
TASK [Chrony points at the site NTP servers] ***
--- before: chrony.conf
+++ after: chrony.conf
@@ -1,3 +1,3 @@
 server 10.0.0.1 iburst
-server 192.0.2.99 iburst
+server 10.0.0.2 iburst
 makestep 1.0 3

changed: [localhost]
localhost                  : ok=1    changed=1
```

- `changed=1` in check mode means drift; the file is still untouched
  - The exit code is still 0, so a pipeline must read the recap (or a JSON callback), unlike Terraform's exit code 2
- Remediate by running the playbook normally
- Agent-based tools correct drift on a schedule: a Puppet agent run every 30 minutes by default

:::exam
- Exit codes for `terraform plan -detailed-exitcode`: 0 means no changes, 2 means changes (drift), 1 means an error. A scenario about "alert when production no longer matches code" wants this flag in a scheduled job.
- State locking prevents two concurrent applies from corrupting state. Remote state in a shared, encrypted, locked backend is the answer for teams; committing `terraform.tfstate` to Git is always a wrong answer.
- Drift remediation depends on which side is correct: re-apply to undo the change, update the code to keep it, refresh-only to accept it into state, import to adopt an unmanaged resource.
:::
