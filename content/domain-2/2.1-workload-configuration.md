### Workload configuration
- ==Workload configuration== is the settings on the workload itself: which certificate a server presents, who may read its key, what traffic a router permits
- Manage it like infrastructure: in Git, applied by a tool, checked for drift
  - A certificate renewed by hand on one node, or an ACL line typed in during an outage, is drift
- The objective names two: ==certificates== and ==access control lists (ACLs)==

### Certificate building blocks
- A ==certificate authority (CA)== signs certificates; clients trust whatever chains back to a CA they already trust
  - Public CAs for internet-facing names; an internal CA (or HashiCorp Vault PKI) for lab and private names
- ==Chain of trust==: server (leaf) certificate, signed by an intermediate, signed by the root
  - The server sends its own certificate plus the intermediates; the client already holds the root
- ==Certificate signing request (CSR)==: the public key and the requested names, sent to the CA; the private key never leaves the server
- ==Subject Alternative Name (SAN)==: the DNS names and IPs the certificate is valid for
  - Clients check the SAN, not the CN; a missing SAN fails validation
- Validity dates: `notBefore` and `notAfter`
  - Public TLS certificates: 200 days maximum since March 15, 2026; 100 days from March 2027; 47 days from March 2029

### Creating a CA and server certificate
```sh label="Lab CA and server certificate"
# 1. Root CA: key and self-signed cert, 10 years
openssl req -x509 -newkey ec \
  -pkeyopt ec_paramgen_curve:P-256 \
  -nodes -keyout ca.key -out ca.crt -days 3650 \
  -subj "/CN=Lab Root CA"
# 2. Server key and CSR with a SAN
openssl req -newkey ec \
  -pkeyopt ec_paramgen_curve:P-256 \
  -nodes -keyout web.key -out web.csr \
  -subj "/CN=web01.lab.example" \
  -addext "subjectAltName=DNS:web01.lab.example"
# 3. The CA signs the CSR: 90-day certificate
openssl x509 -req -in web.csr -CA ca.crt \
  -CAkey ca.key -CAcreateserial -days 90 \
  -copy_extensions copy -out web.crt
```

- Inspect before you deploy

```console label="Terminal"
$ openssl verify -CAfile ca.crt web.crt
web.crt: OK
$ openssl x509 -in web.crt -noout -enddate
notAfter=Jan 17 13:02:54 2027 GMT
$ openssl x509 -in web.crt -noout -checkend 2592000
Certificate will not expire
$ openssl x509 -in web.crt -noout -checkend 8640000
Certificate will expire
```

- `-checkend <seconds>` exits 0 if still valid that far ahead, 1 if not; 2592000 seconds is 30 days, so a renewal job acts on exit code 1
- `openssl verify -verify_hostname db01.lab.example` fails with "hostname mismatch": the SAN does not cover that name

### Deployment and renewal automation
- Certificates as code: the Terraform `tls` provider builds the same CA and server certificate (`tls_private_key`, `tls_self_signed_cert`, `tls_cert_request`, `tls_locally_signed_cert`); the `local.*` values point at the CA key, CA certificate, and CSR

```hcl label="web.tf (excerpt)"
resource "tls_locally_signed_cert" "web" {
  cert_request_pem   = local.web_csr
  ca_private_key_pem = local.ca_key
  ca_cert_pem        = local.ca_cert

  validity_period_hours = 2160 # 90 days
  early_renewal_hours   = 720  # 30 days left
  allowed_uses = [
    "digital_signature",
    "server_auth",
  ]
}
```

```console label="Terminal"
$ terraform output web_ready_for_renewal
false
```

- When 30 days remain, `ready_for_renewal` turns true and the next `terraform apply` replaces the certificate
- The generated private keys are stored in the state file in plain text; this is a lab pattern, and state must be protected

| Tool | Where | How renewal happens |
|---|---|---|
| certbot and other ==ACME== clients | Linux web servers | timer runs `certbot renew`, then reloads the service |
| cert-manager | Kubernetes | controller renews `Certificate` resources into Secrets |
| AWS Certificate Manager | load balancers, CloudFront | managed renewal of ACM-issued certificates |
| Vault PKI | internal services | short-lived certificates issued on demand |

- ==ACME== (RFC 8555) is the protocol Let's Encrypt uses: prove control of the name, receive a certificate, repeat before expiry

### File ACLs
- Mode bits allow one owner, one group, and everyone else; a file ==ACL== adds entries for more users or groups without changing ownership
  - Scenario: the `www-data` group must read one private key that `root` owns with mode `0600`

```console label="Terminal"
$ chmod 600 tls/web.key
$ setfacl -m g:www-data:r tls/web.key
$ getfacl -p tls/web.key
# file: tls/web.key
user::rw-
group::---
group:www-data:r--
mask::r--
other::---
```

- `ls -l` shows a `+` after the mode (`-rw-r-----+`) when an ACL exists
- The ==mask== caps what named users and groups can get; `chmod` on the group bits changes the mask
- `setfacl -d -m g:www-data:r tls` sets a ==default ACL==: new files in `tls/` inherit the entry
- `setfacl -x g:www-data` removes one entry, `setfacl -b` all of them; as code: Ansible `ansible.posix.acl`; Windows NTFS ACLs with `icacls`, `Set-Acl`, or `ansible.windows.win_acl`

### Network ACLs as code
- A network ACL is an ordered rule list that permits or denies traffic by address, protocol, and port
  - Evaluated top down; the ==first match== wins
  - Anything not matched hits the ==implicit deny== at the end
:::wide
| Filter | Stateful? | Rules | Default |
|---|---|---|---|
| Router ACL (Cisco IOS) | No: return traffic needs its own rule | permit and deny, numbered, first match wins | implicit deny |
| AWS network ACL (subnet) | ==Stateless==: allow ephemeral ports 1024-65535 back | allow and deny, lowest rule number first | default NACL allows all; custom NACL denies all |
| AWS security group (interface) | ==Stateful==: replies are allowed automatically | allow only, all rules evaluated | deny all inbound |
:::

- Keep the rules as data, render the device syntax from a template

```yaml label="acl_vars.yml"
acl_name: WEB-IN
web: host 10.20.1.10
rules:
  - seq: 10
    action: permit
    src: any
    port: 443
  - seq: 20
    action: permit
    src: host 10.99.0.5
    port: 22
```

```django label="acl.j2"
ip access-list extended {{ acl_name }}
{% for r in rules %}
 {{ r.seq }} {{ r.action }} tcp {{ r.src }}
 {{- " " ~ web ~ " eq " ~ r.port }}
{% endfor %}
 1000 deny ip any any log
```

- An `ansible.builtin.template` task writes `WEB-IN.cfg` (`{{-` joins the two template lines); the explicit last rule logs what the implicit deny would drop silently
- Add rule 30 (HTTP) to the data, then preview the change before it reaches the router

```console label="Terminal"
$ ansible-playbook acl.yml --check --diff
@@ -1,4 +1,5 @@
 ip access-list extended WEB-IN
  10 permit tcp any host 10.20.1.10 eq 443
  20 permit tcp host 10.99.0.5 host 10.20.1.10 eq 22
+ 30 permit tcp any host 10.20.1.10 eq 80
  1000 deny ip any any log
```

- Push with the `cisco.ios.ios_acls` module; `state: overridden` also deletes lines not in the data, which fixes ACL drift

:::exam
- Expiry questions: `openssl x509 -checkend` or `-enddate` finds certificates about to expire; the fix in a scenario is automated renewal (ACME, cert-manager, ACM, or a pipeline job), not a calendar reminder. A browser error on one hostname usually means that name is missing from the SAN.
- Give one more group access to one file without changing its owner or group: `setfacl`, not `chmod 777` or `chown`.
- Network ACLs are ordered and end in an implicit deny; a new permit placed after a broader deny never matches. NACLs are stateless; security groups are stateful.
:::
