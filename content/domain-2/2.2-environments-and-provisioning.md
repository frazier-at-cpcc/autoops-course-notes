### Two ways to write the automation
- ==Imperative==: you write the steps and their order
  - Bash and PowerShell scripts, database migrations, a runbook turned into code
  - The script does exactly what it says, even when the step is no longer needed
- ==Declarative==: you write the end state; the tool works out the steps
  - Ansible tasks, Terraform, Kubernetes manifests, Compose files
  - Run it again and only the differences change
- Objective 1.3 covers the IaC theory (state, idempotency); here the question is which to reach for
  - Imperative: one-time changes, strict ordering, glue between tools
  - Declarative: configuration that must stay in a known state
- Most real automation mixes the two
  - A playbook is an ordered list (imperative) of declarative tasks

### Script writing
- ==Script writing== is the imperative approach done carefully
  - Fail fast: `set -euo pipefail` stops on an error, an unset variable, or a broken pipe
  - Check before you change, so a second run is harmless
  - Print what changed, and exit 0 only on success; cron, CI, and Ansible trust the ==exit code==

```bash label="bootstrap-node.sh"
#!/usr/bin/env bash
# Imperative: steps run in the order written
set -euo pipefail
conf="${NODE_ROOT:-}/etc/chrony.sources"
mkdir -p "$(dirname "$conf")"
if grep -qs '^server 10.0.20.5' "$conf"; then
  echo "ntp: already set, no change"
else
  echo "server 10.0.20.5 iburst" >> "$conf"
  echo "ntp: added 10.0.20.5"
fi
```

```console label="Terminal"
$ ./bootstrap-node.sh
ntp: added 10.0.20.5
$ ./bootstrap-node.sh
ntp: already set, no change
```

- Every guard is code to write and test; the declarative `copy` task in `local.yml` (below) needs no `if`

### Migrations
- A schema ==migration== is a small, versioned script that changes a database one step
  - Applied in order, each once; never edit one that has run, add a new one
  - An `up` section and, where possible, a `down` to roll back
  - The tool records what ran in a table (`schema_migrations`)
  - Flyway, Liquibase, Alembic, dbmate, golang-migrate, Django, Rails
- Migrations are imperative; ==state-based== tools (Atlas, SSDT) diff a desired schema against the live one, the declarative style

```sql label="20261015090000_add_site.sql"
-- migrate:up
ALTER TABLE devices ADD COLUMN site TEXT
  NOT NULL DEFAULT 'CLT1';

-- migrate:down
ALTER TABLE devices DROP COLUMN site;
```

```console label="Terminal"
$ export DATABASE_URL=sqlite:db/net.db
$ dbmate status
[X] 20261001090000_create_devices.sql
[X] 20261008090000_add_mgmt_ip.sql
[ ] 20261015090000_add_site.sql

Applied: 2
Pending: 1
$ dbmate up
Applying: 20261015090000_add_site.sql
Applied: 20261015090000_add_site.sql in 1.368997ms
$ sqlite3 db/net.db 'SELECT * FROM schema_migrations'
20261001090000
20261008090000
20261015090000
```

- `dbmate rollback` runs the newest `down` section; timestamped names keep two branches from claiming the same version
- Infrastructure has migrations too: Terraform `moved` blocks relocate resources in state without rebuilding them

### Push and pull provisioning
- ==Push==: a control node sends the change when you run it
  - `ansible-playbook` over SSH or WinRM, Salt's master, `terraform apply`
  - Immediate and ordered: drain, patch, reboot, rejoin
  - Needs a path and credentials to every target; an offline node misses the run
- ==Pull==: each node asks for its configuration on a schedule
  - Puppet and Chef agents, `ansible-pull` from cron, `cloud-init` at first boot, GitOps (Argo CD, Flux)
  - Scales out; outbound-only; drift corrected at the next check-in
  - Changes land within one interval; ordering across nodes is harder

:::figure wide 2.2-push-pull.svg | Push: the control node starts the run and connects out to every target. Pull: each node starts its own run and fetches its configuration from a central source.

```yaml label="local.yml (in the Git repo)"
- name: Baseline this node
  hosts: localhost
  connection: local
  gather_facts: false
  vars:
    root: "{{ lookup('env', 'NODE_ROOT') }}"
  tasks:
    - name: Declare the NTP sources file
      ansible.builtin.copy:
        dest: "{{ root }}/etc/chrony.sources"
        content: "server 10.0.20.5 iburst\n"
        mode: "0644"
```

```console label="Terminal (on the node)"
$ REPO=file://$PWD/node-config.git
$ ansible-pull -U "$REPO" -i localhost, local.yml
Starting Ansible Pull at 2026-10-19 08:54:48
PLAY [Baseline this node] *****
TASK [Declare the NTP sources file] *****
changed: [localhost]
PLAY RECAP *****
localhost                  : ok=1    changed=1
$ ansible-pull -o -U "$REPO" -i localhost, local.yml
Repository has not changed, quitting
```

- In production `REPO` is an HTTPS URL and cron runs this every 15 to 30 minutes; `-o` (`--only-if-changed`) skips the play when Git has nothing new

### Ephemeral and persistent environments
- ==Ephemeral environment==: built from code on demand, thrown away after
  - A review app per pull request, CI service containers, a lab that `terraform destroy` removes at 6 p.m.
  - Proves the code builds everything from nothing: a fresh database runs all three migrations in order
- ==Persistent environment==: production, staging
  - Holds real data; changed in place, one pending migration at a time

| | Ephemeral | Persistent |
|---|---|---|
| Lives for | Minutes to days | Months to years |
| Data | Seeded, disposable | Real, backed up |
| Changed by | Rebuild from code | Change in place |
| Drift | None | Detect and correct |
| Cost | Only while running | Always on |

:::exam
- "Nodes check in with a server and apply their configuration on a schedule" is pull (agent-based). "One command configures every server now" is push.
- Ephemeral environments are built per test or pull request and destroyed after; persistent ones keep data. Clean test runs and lower cost point to ephemeral.
- Migrations are ordered, versioned scripts tracked in a table. Fix a bad one with a new migration or a rollback, not by editing it.
:::
