### Where the code runs
- ==Local== automation runs on the machine it changes
  - A script on a server, a scheduled task on a workstation, a playbook with `connection: local`
- ==Remote== automation runs from a control node and reaches targets over the network
  - One controller, hundreds of switches and servers
  - Needs a transport, credentials, and a firewall path to every target
- Three ways to reach a remote target

:::wide
| Approach | Transport and port | Needs on the target |
|---|---|---|
| ==Secure Shell (SSH)== | TCP 22, key-based login | `sshd`; Python for most Ansible modules |
| ==Windows Remote Management (WinRM)== | TCP 5985 (HTTP) or 5986 (HTTPS) | WinRM listener and PowerShell |
| ==Agent-based== | Agent calls the server, such as Puppet on TCP 8140 | Installed agent and its certificate |
| Local | None | The script and its interpreter |
:::

### Remote over SSH
- The default remote channel for Linux, Unix, and network gear
  - Encrypted, with ==key-based authentication==; no password typed
- `BatchMode yes` makes `ssh` fail instead of prompting
  - A script waiting on a password prompt hangs the pipeline
- A per-project `ssh_config` keeps hosts, ports, and keys out of the command line

```text label="ssh_config"
Host lab-srv1
  HostName 127.0.0.1
  Port 18250
  User netops
  IdentityFile ./id_ed25519
  BatchMode yes
  StrictHostKeyChecking accept-new
  UserKnownHostsFile ./known_hosts
```

```console label="Terminal"
$ ssh -F ssh_config lab-srv1 'uname -n; id -un'
lab-srv1
netops
```

- Ansible is ==agentless==: it rides the same SSH connection
  - Copies a small module to the target, runs it with Python, deletes it
  - Network devices use `network_cli` instead: the module runs on the controller and sends CLI commands over SSH

```ini label="inventory.ini"
[linux]
lab-srv1 ansible_host=127.0.0.1 ansible_port=18250

[linux:vars]
ansible_user=netops
ansible_connection=ssh
ansible_python_interpreter=/usr/bin/python3
```

```console label="Terminal"
$ ansible linux -i inventory.ini -m ping
lab-srv1 | SUCCESS => {
    "changed": false,
    "ping": "pong"
}
$ ansible linux -i inventory.ini -a "uname -n"
lab-srv1 | CHANGED | rc=0 >>
lab-srv1
$ ansible linux -i inventory.ini -m ping -vvv
<127.0.0.1> ESTABLISH SSH CONNECTION FOR USER: netops
PUT .../tmpm30q4kv1 TO .../AnsiballZ_ping.py
```

- `-m ping` is not ICMP
  - It proves the login works and the target has a usable Python

### Remote over WinRM
- WinRM is Microsoft's implementation of the WS-Management standard
  - SOAP messages over HTTP; PowerShell Remoting rides on it
  - ==5985== is HTTP, ==5986== is HTTPS
  - On 5985, Kerberos or NTLM still encrypts the message body; Basic auth does not, so use 5986 with a certificate
- Turn it on with `Enable-PSRemoting` (or `winrm quickconfig`)
- ==PowerShell Remoting==: `Invoke-Command -ComputerName win-dc1` runs a script block remotely; `Enter-PSSession` opens an interactive shell
- Ansible: `ansible_connection: winrm` (or `psrp`), plus the `ansible.windows` modules
- Current Windows ships an OpenSSH server, so SSH to Windows is also an option

```yaml label="windows.yml"
windows:
  hosts:
    win-dc1:
      ansible_host: win-dc1.corp.example.com
  vars:
    ansible_connection: winrm
    ansible_port: 5986
    ansible_winrm_scheme: https
    ansible_winrm_transport: kerberos
```

- Kerberos needs the host name, not an IP address, and a domain-joined target
- No Windows host here: the test only checks this inventory with `ansible-inventory`

### Agent-based automation
- An ==agent== is a service installed on every managed node
  - It connects out to a server, fetches its configuration, applies it, and reports back
  - No inbound port on the node; works behind NAT

:::wide
| Tool | Agent | Talks to | Default rhythm |
|---|---|---|---|
| Puppet | `puppet agent` | Puppet server, TCP 8140 | Every 30 minutes |
| Chef Infra | `chef-client` | Chef Infra Server, HTTPS | Every 30 minutes as a service |
| Salt | `salt-minion` | Salt master, TCP 4505 and 4506 | Persistent link; master sends jobs at once |
| AWS Systems Manager | `amazon-ssm-agent` | SSM endpoints, HTTPS 443 | Polls for commands |
:::

- Costs: install and patch the agent, manage its certificates, CPU and memory on every node
- Gains: continuous ==drift== correction, no credentials for every node on one controller
- Agentless costs the opposite: inbound access and stored credentials, but nothing to install

### Local: command-line scripts
- A ==command-line script== runs where it lives: Bash, PowerShell, or Python
  - ==Shebang== line (`#!/usr/bin/env bash`), `chmod +x`, exit code 0 for success
  - Started by hand, by `cron` or a systemd timer, or by Task Scheduler on Windows
- Remote tools often deliver local scripts
  - Ansible's `script` module copies a script to the target and runs it there
- Ansible can also run locally: `-c local` skips SSH entirely
  - Used for cloud and controller APIs, where the "target" is an HTTPS endpoint

```console label="Terminal"
$ ansible localhost -c local -m ping
localhost | SUCCESS => {
    "changed": false,
    "ping": "pong"
}
```

### Foreground and background
- ==Foreground==: the shell waits and the job owns the terminal
  - Ctrl+C stops it; Ctrl+Z suspends it
- ==Background==: `&` returns the prompt at once
  - The shell prints a job number and a PID
- `jobs` lists them; `fg %n` and `bg %n` move them; `kill %n` ends them
  - `kill -STOP %1` below does what Ctrl+Z does at the keyboard

```console label="Terminal"
$ ./poll-switches.sh &
[1] 17895
$ jobs
[1]+  Running                 ./poll-switches.sh &
$ kill -STOP %1
[1]+  Stopped                 ./poll-switches.sh
$ bg %1
[1]+ ./poll-switches.sh &
$ sleep 1 &
[2] 18038
$ fg %2
sleep 1
$ kill %1
[1]+  Terminated              ./poll-switches.sh
$ nohup ./poll-switches.sh >poll.log 2>&1 &
[1] 18079
$ disown %1
$ jobs
```

- Background jobs die with the terminal unless protected
  - ==nohup== ignores the hangup signal sent at logout
  - `disown` removes the job from the shell's table
  - Anything that must always run belongs in a systemd service, not a shell job
- PowerShell: `Start-Job`, `Get-Job`, `Receive-Job`
  - `Invoke-Command -AsJob` runs remote work in the background
  - PowerShell 7 also accepts `&` at the end of a pipeline

```powershell label="backup-job.ps1"
Start-Job -Name backup -ScriptBlock {
    Start-Sleep -Seconds 2
    "Saved 14 configs"
} | Out-Null
Get-Job | Format-Table Id, Name, State
Receive-Job -Name backup -Wait -AutoRemoveJob
```

```console label="Terminal"
$ pwsh -File backup-job.ps1
Id Name   State
-- ----   -----
 1 backup Running

Saved 14 configs
```

:::exam
- Match the port to the protocol: SSH is 22, WinRM is 5985 for HTTP and 5986 for HTTPS. "Manage Windows hosts remotely with no agent" points to WinRM (or SSH on newer Windows).
- Agent-based means software on every node that checks in with a server; agentless (Ansible) means the controller connects in over SSH or WinRM. A node behind NAT with no inbound access suits an agent.
- A long job that must survive logout needs `nohup` or a service; `&` alone only frees the prompt.
:::

:::try
Start `sleep 300 &` and run `jobs -l`. Bring it forward with `fg`, suspend it with Ctrl+Z, resume it with `bg`, and end it with `kill %1`, running `jobs -l` after each step to watch the state change while the PID stays the same.
:::
